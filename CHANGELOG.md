# Changelog

All notable changes to spakr are recorded here, newest first. Versions are `MAJOR.MINOR.BUILD`; BUILD counts up with every push to `main` (see [`scripts/version.sh`](scripts/version.sh)), so entries are written per MAJOR.MINOR tier and name the TODO ids they close. Format follows [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

### Added
- Required-components research (RES.33 done, docs/research/components.html): the best way to describe components is a C4 container view plus a fixed-column catalogue; 68 components across platform, accounts, web security, content model, rendering, storage, media, discovery, moderation, mail, operations and interface, each ranked S1 to S4 for security with efficiency notes and its TODO ids. Lists the gaps (login throttling timing, MFA decision, session management, account lifecycle, database privileges, systemd sandboxing, vulnerability scan, infobox rendering, mod tools, upgrade and maintenance mode) for the TODO thread.
- Version control system research (RES.34 done, docs/research/vcs-choice.html, poc/vcs_bench.py): git compared with Subversion, Mercurial and Fossil by measurement and with Jujutsu, Pijul and Dolt by desk review; git confirmed, Subversion the only close rival.
- Calm responsive UX research (RES.32 done, docs/research/web-ux.html): keeps the Research C stack and adds ten calm rules, a single-column-first layout with optional rails, per-setting themes that change only accent, tint and heading font (palettes generated and contrast-checked), icon licence check (Lucide is ISC plus MIT, so two notices), a no-JavaScript fallback for every interactive component, and an editor with a typed-field form. New items UX.29 to UX.35 and UI.24. Owner accepted both recommendations: setting themes change accent, tint and heading font only, and no phone bottom tab bar.
- Health and status (API.8): `/api/v1/health` reads the real database schema version through `spakr.db` and reports `ok`, `needs-upgrade`, `newer-than-code`, `uninitialised` or `unavailable`; anything but `ok` makes the overall status `degraded` (HTTP 503). The duplicate `spakr/db/versions.py` shim is removed.
- Content-side research (RES.1, RES.2, RES.3, RES.4, RES.7, RES.8, RES.10, RES.11 done; new RES.25 caching done) as pages under `docs/research` with a research index, backed by experiments on Ubuntu 24.04: Markdown engines compared, MathML maths with Temml, the nh3 sanitiser against 23 hostile inputs, git access benchmarks and a locking test, MySQL FULLTEXT trials up to 50,000 pages, ImageMagick policy and ffmpeg checks, a strict-CSP browser test and cache timings. Prototype scripts in `docs/research/poc/`; tested ImageMagick policy in `examples/imagemagick-policy.xml`.
- New item RND.7 (link-status pass after the render cache).
- Content store research (RES.29 done): git versus MySQL for page content measured on this machine (saves, concurrency, history, blame, growth, backups) and corruption trials (git fsck detection, par2 repair of a damaged pack, InnoDB page damage). Recommendation: keep git as the source of truth with a rebuildable MySQL index; new item GIT.9 (complete front matter). Feeds RES.26, RES.27 and the INT items. Benchmark script `docs/research/poc/store_bench.py`.

- Application shell and navigation planned (UX.1 to UX.24, issue #56): top bar with tab navigation for tools, settings and account and a hamburger that opens the site table of contents and links in a left drawer; page table of contents, page actions and related entries in a right rail; a footer with software name and version, licence and the GitHub link. Basics (design spec, tokens, shell layout, top bar, drawer, rail, footer with the health-endpoint version, responsive rules, theme and TV toggles, accessibility and Playwright shell tests) are in 0.1; page TOC in 0.3; role-aware menus in 0.4; site TOC, breadcrumbs and related entries in 0.6; page actions, tools, settings and search in 0.8. - Logo space in the top-left of the top bar (UX.25 to UX.28, MED.30, MED.31): the logo is uploaded from the admin settings through the normal upload interface; a queue task derives favicon, Apple touch icon, manifest and maskable icons and a social image from it (never enlarged, minimum source size, SVG only if the upload policy allows), regenerated when the logo changes; head tags and manifest come from settings; a text wordmark is the fallback.
- Secrets in backups decided (RES.31): backups hold a redacted config.json; secrets are re-entered on restore; archives for the off-host copy may be encrypted.
- Backup and recovery pipeline planned (BAK.1 to BAK.27, RES.30 and RES.31, issue #54): nightly backups in `/data/backups` with a par2 parity set per backup, tar.bz2 by default and tar.gz as an option, checksum manifest, verify after write, retention, restore and drill commands, an off-host copy hook, status in health and alerts through the mail relay, hardening (0700/0600, never web-served), and round-trip and damage-and-repair tests. Earliest basics (settings, layout, manifest, MySQL dump, config policy, archive, parity, `spakr backup` and `spakr restore`) are in 0.1. DB.4 moved to 0.1 as restore support and OPS.5 became the clean-install acceptance test.
- Integrity principle (owner decision): the system is built with checksums and parity data so a damaged database or store can be detected and rebuilt. New INT category (INT.1 to INT.16) and research items RES.26 (parity options), RES.27 (source of truth versus rebuildable) and RES.28 (checksum design): data classification, migration and row checksums, a hash-chained audit log, hash manifests, git fsck, parity for the content store and media, a journal of MySQL-only data, `spakr verify` with scheduled verification, integrity in health and status, `spakr repair`, an admin screen, and damage-and-recover tests. DB.3 now rebuilds all derived data; OPS.5 backups include manifests and parity.
- No Node.js anywhere (owner decision): maths renders to MathML in pure Python with latex2mathml behind guards (aligned rewrite, size cap, output check, TeX-source fallback); RES.2 and RND.2 updated, the vendored Node script and Temml are removed from the plan and research pages, and `nodejs` is no longer an install dependency. Research C's no-Node recommendation stands.
- Media planned as a full management suite (MED.11 to MED.29, UI.20 to UI.23, DOC.8): metadata, usage index and orphan detection, library API and screens, per-file visibility, replace and re-process without breaking embeds, variants regeneration, moderation queue, duplicate detection, bulk actions, storage quota, takedown handling, and prune-media (dry run by default, grace period, history references decided in MED.23, locking, audit entry per run, `scripts/prune-media`, systemd service and timer, admin API and screens).
- Layout clarified: `config.json` lives in the project root; `/data` holds only the articles and system data (content repository, media, originals, uploads, cache); examples and docs never go in `/data`. New item for the build thread to drop the data-directory config fallback (FND.12).
- Markdown is Python-Markdown with MultiMarkdown-style extensions and YAML front matter (no true MultiMarkdown engine is packaged for Ubuntu 24.04); maths is rendered to MathML by Temml; sanitising is nh3 with a fixed Markdown baseline plus admin-approved tags (RND.1 to RND.3). Plan pages (architecture, content, data model, deployment) updated to match.
- Git access is the `git` binary under an exclusive `flock` (GIT.1); rendered pages are cached by content key in per-process memory plus disk, with no Redis (RND.5, SEARCH.10, now needing RES.25).
- Search: MySQL FULLTEXT server settings (`innodb_ft_min_token_size=2`, stopwords off) are an install requirement with a start-up check, not admin web settings (SEARCH.8); the search document adds split and joined token forms (SEARCH.2).
- Media: one ImageMagick process writes the whole width ladder under a tight policy file; ffmpeg runs with a protocol whitelist and timeouts (MED.4, MED.5).
- Open questions added: accept a MultiMarkdown-compatible dialect (RES.1) and Node.js at runtime for maths (RES.2).

### Added
- Web layer research (RES.11, RES.21, RES.22, RES.23, RES.24 done): three pages under `docs/research` (web-layer, web-devices, web-components) and a tested responsive prototype in `docs/research/web-prototype` (reading page, editor, light and dark, TV mode; 36 page loads at phone to 4K sizes with no overflow, no axe-core violations and no CSP violations). Decisions proposed: no Node.js anywhere in the product, hand-written modern CSS with tokens, no-build vanilla ES modules (Preact with htm held in reserve), textarea editor with server preview, native dialog lightbox and media controls, Lucide icon sprite, system fonts, manifest without service worker.
- New items UI.17 (Python asset tooling and size budgets), UI.18 (web app manifest), UI.19 (search combobox and link picker).
- Database layer (DB.1, DB.5, first part of DB.2): `spakr.db` with a SQLAlchemy engine (MySQL through PyMySQL, utf8mb4, optional unix socket), Alembic migrations 0001 (schema version, config, users, roles and permissions with seeds, settings, audit log) and 0002 (pages, aliases, revisions, tags, relation kinds, relations, links), and an integer schema version in the `schema_version` table that counts up with every migration (`get_schema_version`, `SCHEMA_VERSION`, `schema_status`). `spakr init-db` creates the data folders and applies migrations; `spakr db-version` prints applied and expected versions. Tests run on SQLite always and on MySQL 8 when `SPAKR_TEST_DATABASE_URL` is set (the daily workflow starts a MySQL service).
- Flask API skeleton (API.1, API.7, FND.4): app factory `spakr.api.create_app()` and `spakr/wsgi.py` for Apache mod_wsgi (daemon mode, pass-authorization on); `GET /api/v1/health` reports status, configuration state, the software version (MAJOR.MINOR.BUILD), the integer API version and the database schema version (`unknown` until the database layer lands); a missing or invalid `config.json` leaves the app running, health says `not_configured` (HTTP 503) and every other route answers a 503 problem. All errors are `application/problem+json` with a request id (`X-Request-ID`); every response carries `X-API-Version`; JSON-lines logging to stderr without query strings; OpenAPI served at `/api/v1/openapi.json`. The API version is one constant (`spakr/api/versions.py`); a test fails if the generated OpenAPI description differs from `tests/api_contract.snapshot` or changes without a higher version than main. Shared outbound User-Agent helper `spakr/outbound.py` (`spakr/<version> spakr-api/<n> (+contact)`).
- Python package skeleton in `src/spakr` with `pyproject.toml` (Python 3.12 or newer, start-up error otherwise), data paths under `/data` (`SPAKR_DATA_DIR` and `SPAKR_CONFIG` overrides), the software version helper and the first tests (FND.1, FND.10).
- Package skeleton and config loader (FND.1, FND.2, CFG.3): `src/spakr` package for Python 3.12, `pyproject.toml`, frozen settings objects with a `Secret` wrapper, `python -m spakr check-config|version`. A missing or invalid `config.json` ends with a clear message and exit status 2, never a traceback. `paths.data_dir` (default `/data`, git-ignored; `SPAKR_DATA_DIR` overrides it for tests) holds all runtime data.
- Platform and security research (RES.5, RES.6, RES.9, RES.12, RES.14, RES.15, RES.16, RES.17, RES.18, RES.20 done) as pages under `docs/research`, with experiments run on Ubuntu 24.04: Flask, pydantic and argon2 under apt mod_wsgi, file-type sniffing, an OpenAPI spike and atomic `config.json` rewrites under contention. Plus a platform conventions page (queue, logging, MySQL, outbound HTTP, testing and CI, privacy).
- New suggested items: AUTH.12 (user data export), MED.9 (optional ClamAV scan), MED.10 (captions and transcripts), DOC.7 (privacy page).

### Changed
- Decisions for the first build: Python 3.12 required (FND.10); integer database and API versions that count up on every change (DB.5, API.7), reported with the software version by the health and status endpoint (API.8); all data under git-ignored `/data` (FND.11); graceful failure without a config file (CFG.8). `/data/` added to `.gitignore`; config example paths moved under `data`.
- Web UI layer research added for Research C: RES.21 to RES.24 (CSS and design system, Node.js justification, device range from phone and foldable to TV, component approach) and UI.15 (TV and foldable layouts), UI.16 (device test matrix); UI.1, UI.11, UI.12 and UI.13 now need the matching research.
- Assumption recorded: Apache2 handles TLS and a valid domain certificate is in place; no certificate handling in the app. Added API.6 (trust Apache HTTPS signal, Secure and __Host- cookies, HSTS only if the admin enables it).
- CSRF design is a synchronizer token tied to the server session plus a Fetch Metadata check, replacing the double-submit token (RES.5, AUTH.2); invitation and reset tokens travel in the URL fragment and are consumed by a POST (AUTH.4, AUTH.5); API keys cannot manage keys or account security (AUTH.6).
- Hosting: apt mod_wsgi in daemon mode must set `WSGIPassAuthorization On` or the app never sees `Authorization: Bearer` (verified), plus `WSGIApplicationGroup %{GLOBAL}` (FND.3, FND.6).
- Packaging: Python libraries come from a hashed virtualenv lock, not apt (24.04 ships SQLAlchemy 1.4 and pydantic 1.10); PyMySQL (MIT) is the MySQL driver instead of the GPL mysqlclient (FND.1, DB.1).
- Backups become one `spakr backup` / `spakr restore` command pair (OPS.5, FND.9); the daily CI run opens an issue when it fails (FND.7); API validation and OpenAPI use pydantic v2 with SpecTree (API.3).
- Git commits use a pseudonymous per-account identity so history never holds personal data (GIT.1, conventions page).

### Changed
- Decided: the app rewrites `config.json` atomically at mode 0600; secret fields are write-only in the UI. RES.20 now only confirms implementation details (CFG.5).
- Email goes through an external SMTP relay, never a local MTA; relay settings and sender address are configuration (MAIL.1 unblocked, RES.6 reworded).
- Media: ffmpeg and ImageMagick are the preferred tools; Python libraries allowed where measurably better (RES.10, MED.4).
- Config: secrets live in `config.json`, everything is editable in the web interface except the MySQL credentials. Admin settings API (AUTH.8) never returns secrets.
