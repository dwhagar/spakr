Process model

  • Flask app (WSGI): the versioned JSON API under /api/v1/ plus the server-rendered web UI, which is a client of that API. See platform services.
  • CGI: only for a few small scripts, never the main app; kept for tiny, isolated endpoints (health check, upload receiver if separate privileges are wanted). Same code library as the WSGI app.
  • Worker: systemd service consuming the Redis queue. Jobs: render cache warm, reindex, upload scanning, image and video processing, git maintenance (gc), backups.
  • Git writes are serialised with a lock so concurrent saves cannot corrupt the repository. Each save is one commit authored by the logged-in user.

Application shell

Owner-specified layout (UX category): a top bar with a logo space at its top left (the logo is uploaded through the upload interface from the admin settings and the site icon set is derived from it), tab navigation for tools, settings and account, search, theme and TV toggles, and a hamburger (three lines); a left drawer opened by the hamburger holding the site table of contents and links; a right rail holding the page's own table of contents, page actions and related entries; and a footer showing the software name and version (from the same source as the health endpoint), the licence (MIT code, CC BY-SA content) and a link to the GitHub repository. On wide screens the drawer is a persistent column that the hamburger collapses; on narrow screens it is an overlay and the rail moves under the page title. Menu items are driven by role (reader, editor, GM, mod, admin); the API still enforces every permission.

Integrity and recovery

Built in from the start (owner decision): every stored artifact has a checksum, parity data protects the content store and media, and every artifact is classed as source of truth or rebuildable. Working classification, to be confirmed by RES.27 and recorded in INT.1:

DataClassRecovery
Pages (git content store)Source of truthParity data, git fsck, backups
Media originalsSource of truthHash manifest, parity data, backups
Accounts, settings, audit, invitations (MySQL only)Source of truthChecksummed journal (INT.9), row checksums, backups
Page index, search tables, relations, usage indexRebuildableRebuilt from the content store (DB.3)
Media variants, rendered-page cacheRebuildableRegenerated from originals and pages (INT.5)

Backups (BAK category): a nightly systemd timer runs spakr backup, which writes a consistent snapshot (MySQL dump, git content store, media originals, config by explicit secrets policy) to /data/backups as tar.bz2 (tar.gz by setting) with a checksum manifest and a par2 parity set per backup, verifies it after writing, rotates old backups and reports status in health and status. spakr restore verifies and repairs the archive from parity before restoring. The directory is mode 0700, owned by a dedicated user and never web-served.

Tools: spakr verify (also scheduled and shown in health and status), spakr repair and the damage-and-recover tests. See the INT category in the tiers.

The web UI is a first-party JavaScript client that calls the API over HTTP and never bypasses it. Outbound HTTP uses one shared client helper with a standards-compliant User-Agent.

Configuration

Every option that holds a secret lives in config.json (git-ignored, mode 0600; .gitignore ignores every *.json); the committed example is examples/config.json.example. The MySQL credentials are configured there manually and are never exposed or editable through the API or web interface. Every other setting is changeable in the admin settings screens backed by the API: non-secret settings live in the database, secrets are written to config.json by the app and are write-only (set or unset, never returned or logged).
