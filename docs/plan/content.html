Content, rendering and security

Allowed content

  • Markdown (MultiMarkdown flavour) and LaTeX math only.
  • These rules cover content. The site's own first-party UI code may use JavaScript from its own origin (see platform); content never can.
  • Raw HTML is stripped by default. The admin keeps an allowlist of simple HTML 1.0/1.1-era tags that Markdown lacks, for example <sup>, <sub>, <u>, <abbr>. Tags are added only by manual admin approval.
  • Allowed tags carry no attributes unless the admin approves specific ones; style, on*, class and id are never allowable. <script>, <style>, <iframe>, <object> and javascript: URLs are never allowable.

Rendering pipeline

  1. Load Markdown from git at the requested commit (default: head).
  2. Extract math spans so they are not mangled by Markdown.
  3. Render with MultiMarkdown (tables, footnotes, citations, definition lists, metadata).
  4. Sanitise the HTML against the allowlist (parse, drop anything not approved, never regex).
  5. Typeset math: default is server-side to static markup (no client script). Client-side MathJax/KaTeX from our own static files is an option if the CSP allows it.
  6. Cache the result keyed by commit hash; the worker invalidates on change.

The site sends a strict Content-Security-Policy with no inline script or style, as a second line of defence.

Embedded media

  • Authors never write HTML for media. They use a Markdown-level syntax that the renderer expands, for example ![Caption](media:video/abc123) or ![Caption](media:audio/abc123), where the id refers to a processed upload. Only processed, published uploads can be referenced.
  • The renderer emits the player markup from an admin-controlled template: HTML5 <video controls> and <audio controls> elements with preload="metadata", one source per transcoded format, a poster for video, and a text fallback link. These elements never pass through the author HTML allowlist, so it stays unchanged, and no script or inline style is involved (native browser controls only).
  • Video thumbnails: use an embedded cover image from the file metadata if present, otherwise extract a frame with ffmpeg.
  • Audio thumbnails: use embedded cover art (for example ID3 album art) if present and shown beside the player; otherwise none.
  • Thumbnails are re-encoded images, handled like any other image upload.
  • The Content-Security-Policy gains media-src 'self'; uploads remain served by the app, not directly from disk.

Revisioning

  • One git repository for content, separate from the code repository. Path: <type>/<slug>.md.
  • Each edit is a commit with the user as author and an optional edit summary.
  • History, diff and revert are available in the UI. Revert creates a new commit; history is never rewritten.
  • Renames keep history by using git mv; slugs redirect.

Uploads

  • Safe by default: images (PNG, JPEG, GIF, WebP), video (MP4, WebM, MOV input), audio (MP3, Ogg, FLAC, WAV, M4A input), plain text, Markdown, CSV. SVG is excluded by default because it can carry script.
  • Admin toggles can enable additional classes such as PDF and archives.
  • Admin override: a file outside the enabled list lands in quarantine and is only published after an admin approves it individually.
  • Processing: images and video are never served as uploaded. A Redis task runs ImageMagick (images) and ffmpeg (video and audio) as sandboxed subprocesses to re-encode, strip metadata and create thumbnails and poster frames; the processed copy is published only if every check passes. See media processing research.
  • Size limits: 10 MB for general files and images, 100 MB for video (admin adjustable).
  • Originals: kept after processing, stored privately outside the web root, never served, and excluded from the public file listing. Admins can purge originals (single file, by age, or all) from the admin screen or a maintenance script. Backups include or exclude them by option.
  • Storage: files are kept in hashed directories with simply named resolution variants; see platform services.
  • Checks: extension and sniffed MIME must agree, size limit, files renamed to their content hash, stored outside the web root and served by the app with X-Content-Type-Options: nosniff and Content-Disposition set appropriately, optional ClamAV scan in the worker.

Copyright

The site links to the copyright notice and removal-request process in COPYRIGHT.md (removal requests go to sysop@moltenaether.com). Mods can disable media or pages immediately while a request is reviewed.

Other security basics

Password hashing with argon2 or bcrypt, CSRF tokens, secure and HttpOnly cookies, parameterised SQL only, rate limiting on login, audit log of admin actions.
