Data model

Every page has a common header (id, slug, type, title, setting tags, summary, created/updated, current git commit) and a Markdown body stored in git. Type-specific fields, tags, settings, visibility, aliases and relations are kept in the page's YAML front matter, which is the authoritative copy (GIT.9), and mirrored in database columns for browsing and filtering, so the whole index can be rebuilt from git alone (RES.29). Each page also stores the SHA-256 of its file (content_sha256) for damage detection.

Settings

One game world per install. Each page carries one or more setting tags: high fantasy modern / cosmic horror science fiction. Settings are data, so admins can add more later. There are no separate campaigns in 1.0.

Visibility

Each page has a visibility field: public (default) or gm. GM-only pages are readable only by users with the GM or admin role. Every query path (view, list, search, backlinks, relations, history, diff, uploads attached to the page) filters on it. The content git repository holds all pages, so it must never be exposed directly and backups must be treated as GM-level.

Rules content

Stat blocks, dice and costs are free text in Markdown tables. There are no typed stat or dice fields in 1.0, so the site stays system-agnostic.

Relations

  • Typed links between pages stored in a relation table (from, to, kind, note), for example character member of nation-state, race grants special ability, item requires skill.
  • Plain wiki links in the Markdown body are parsed into untyped backlinks.
  • Places form a tree through parent_id.

Other tables

users, roles (admin, GM, editor, reader), sessions, settings, html_allowlist, uploads (hash, mime, state, uploader), page_index (for search), audit_log.
