Platform services

Cross-cutting services every tier builds on. Libraries named here are the planned defaults and are to be re-verified against Ubuntu 24.04 packages when 0.1 starts.

Flask API, and everything goes through it

  • The backend is a Flask application served by Apache mod_wsgi (Flask is a WSGI app, so the Apache setup is unchanged). It supersedes the earlier "plain WSGI" default.
  • All reads and writes go through a versioned JSON API under /api/v1/. The web UI is a client of that API over HTTP: the browser runs first-party JavaScript that calls /api/v1, and nothing in the UI touches the database or git directly. Command-line scripts and the worker use the same service layer the API uses.
  • Page delivery: Flask serves a thin HTML shell and static assets; page content for public reading is also rendered server-side from the API's renderer so pages work without JavaScript and are indexable (SEO). Interactive features (editing, account screens, admin screens, uploads, search-as-you-type) are the JavaScript client.
  • JavaScript policy: only first-party scripts served from the site's own origin, versioned and hashed (no inline script, no third-party CDN). Content authors still cannot add script or CSS (see content); the policy applies to the site's code, and the Content-Security-Policy is script-src 'self'.
  • Browser calls: sessions, CSRF, CORS: the UI and API share one origin, so no CORS is needed and cross-origin requests are denied by default (an admin-configured allowlist can enable it for named origins). Login sets a Secure, HttpOnly, SameSite=Lax session cookie; state-changing browser requests must also send a CSRF token in a header (double-submit token issued at login) and are rejected without it. API-key requests send Authorization: Bearer, use no cookies, and need no CSRF token. Responses carry Cache-Control: no-store for authenticated data and Vary: Cookie, Authorization.
  • The API version is a single integer, part of the URL, and reported in the User-Agent (below) and in responses (X-API-Version).
  • Planned libraries: Flask, SQLAlchemy (Core and ORM) with Alembic migrations, marshmallow or pydantic for request validation, Flask-Limiter for rate limits.

Accounts and roles

RoleCan
ReaderView public pages and search; manage own profile and own API keys.
EditorReader plus create and edit pages and upload media; revert own edits.
GMEditor plus see and edit GM-only pages.
ModEditor plus revert any edit, hide or delete pages and media, review quarantined uploads, suspend users temporarily.
AdminEverything: site settings, HTML allowlist, upload policy, roles, all users and keys, purge originals.

Visibility in 1.0 is a single GM-only flag on pages; the database reserves a visibility-group column so groups can come later without a data migration of pages.

Roles are sets of named permissions stored in the database, so admins can adjust them. A user can hold several roles (for example Mod and GM). Anonymous reading is allowed by default.

User and account editing suite (web UI)

  • Self service: profile, display name, email change (with confirmation), password change, active sessions with sign-out, own API keys, notification preferences.
  • Admin and mod screens: list, search and filter users; create, edit, suspend, reactivate and delete accounts; assign roles; force password reset; view audit trail; invite users.
  • Every action is an API call guarded by permissions and written to the audit log.

Email flows

  • Sign-up is by invitation only. There is no public registration endpoint.
  • Invitations: an admin or mod invites an email address with a role; the invitee receives a single-use, expiring link to choose a username and password.
  • Password reset: request by email, single-use expiring link; responses never reveal whether an address exists.
  • Email confirmation for new addresses; security notices for password and email changes.
  • Tokens are random, stored only as hashes, and expire (invitation default 7 days, reset default 1 hour).
  • Mail is sent by queue tasks through SMTP (smtplib with the local MTA or a relay set in the config file), with retries and an outbox table for the admin to inspect failures. Templates are plain text plus simple HTML, stored in the code tree.

API keys and permissions

  • Keys are sent as Authorization: Bearer <key>. A key is shown once at creation; only a hash and a short prefix are stored.
  • Each key has a set of permissions chosen at creation, an optional expiry and IP restriction, a name, and a last-used timestamp. Keys can be revoked at any time.
  • Users create their own keys, and a key can only carry permissions its owner holds. At every request the key's effective permissions are the intersection of the key's permissions and the owner's current permissions, so losing a role immediately limits that user's keys. Users are limited to a configurable number of active keys (default 10).
  • Admins can create unlimited keys, and can create keys for service use that are not tied to a person (owned by a service account).
  • Browser sessions use a cookie with CSRF protection (see above); API-key requests do not use cookies and are exempt from CSRF but rate limited per key.

Outbound HTTP User-Agent

  • Every HTTP request the app makes itself (webhooks, link checks, fetching remote metadata, anything else) goes through one shared helper in src/ that sets the header, so no code builds its own.
  • The string follows RFC 9110: product tokens of the form name/version, plus a comment, with the contact URL in the comment. Format: 
    spakr/1.2.3 spakr-api/1 (+https://your.site.example/about)
    Software name, software version and API version are always present; the contact URL is taken from the site config.
  • Version values come from the single version constant in the code. Tests assert the format.

Media storage layout

  • Files are stored by content hash (SHA-256) in nested directories for easy lookup: the first two byte pairs form the directories, and the whole hash names the leaf directory. 
    media/ab/cd/abcdef0123...full-sha256/
    original.mp4           (private originals live in a separate tree, never served)
    full.jpg               optimized copy at the source size
    w1920.jpg
    w1280.jpg
    w640.jpg
    w320.jpg
    thumb.jpg              small square or poster thumbnail
    poster.jpg             video poster
    cover.jpg              audio cover art, when present
  • Variants are named simply (w<width>, thumb, poster, cover) and sit in the same directory as the hash they belong to. Identical uploads share one directory (deduplication).
  • Gated series, never enlarged: the worker computes the ladder of target widths (for example 1920, 1280, 640, 320) and produces a size only if the source is at least that wide. The first rung at or below the source width is made from the source, each smaller rung is made from the previous one, and nothing is ever scaled up. The full copy is always made, as an optimized re-encode at the source size. A source smaller than the smallest rung gets full and thumb only (thumb never above the source size).
  • Ladder widths and quality settings are admin configuration.
  • Originals are kept privately (see content), in a parallel tree outside the web root.

Caching

  • Memory: per-process LRU for hot small items (sessions' permission sets, settings, allowlist), and Redis for shared cache across WSGI processes. Planned library: Flask-Caching with a Redis backend.
  • Disk: rendered page HTML keyed by git commit hash and visibility, and generated media variants, in a cache directory that is safe to delete (FileSystemCache or plain files). Apache serves static variants with long Cache-Control and ETags because their path contains the hash.
  • Invalidation: a page save bumps its commit hash, which changes the key; the worker prunes stale entries. GM-only output is never put in a cache shared with public output (the key includes visibility).

SEO

  • Public pages get unique titles, meta descriptions (from the page summary), canonical URLs, Open Graph and Twitter card tags, and schema.org JSON-LD (for example Article), generated by one helper from page data.
  • sitemap.xml and robots.txt are generated by the worker; GM-only and private pages are excluded and marked noindex. Redirects for renamed slugs return 301.
  • Candidate libraries (to evaluate in research before 0.3): python-slugify for slugs, a small in-house sitemap writer or flask-sitemapper, and plain Jinja templates for the meta tags. Choose the smallest set that works.
