RES.9: Upload safety and file type checks

Research thread B, 2026-10-17. Unblocks MED.1 and MED.2; feeds MED.3 to MED.5 (thread A owns the media toolchain, RES.10). Builds on media processing.

Recommendation

  • Type detection: python-magic (libmagic) on the first 8 KiB, compared with the extension and an admin-controlled allow-list. Not filetype: it cannot recognise text, CSV or SVG, so it cannot enforce the TXT/MD/CSV and SVG-off policy.
  • Sniffing is only the first gate. Every image is decoded and re-encoded, every audio and video file is probed and transcoded; the re-encoded copy is the only thing served. A file that passes the sniff but fails decoding is rejected.
  • Antivirus: optional, off by default. Provide an admin switch that sends files to a local clamd before processing. The originals are never served, and re-encoding removes embedded payloads from what is served, so the default risk is already low.
  • Safe-list and size limits as decided (PNG, JPEG, GIF, WebP, MP4/WebM/MOV, common audio, TXT, MD, CSV; SVG, PDF and archives off; 10 MB general, 100 MB video, admin adjustable).

That is why the pipeline decodes and re-encodes (Pillow check, then ImageMagick) and never serves the uploaded bytes. Markdown has no signature at all, so the rule for TXT, MD and CSV is: extension in the allow-list, content must be valid UTF-8 with no NUL bytes, size limit, and it is served as plain text.

Handling rules

  • Upload path: stream the request body to a temporary file in the quarantine directory while computing SHA-256 and counting bytes; abort at the limit; never read a whole upload into memory. Mode 0600 (the file's permission bits never carry execute), owned by the app user.
  • Dedupe: if the hash already exists as a published media row, discard the temporary file and reuse the row (the design's deduplication).
  • States: quarantine (just received), processing (queued task running), published or rejected. A rejected file stays for review; mods review, admins override or purge.
  • Image limits: set an explicit maximum pixel count (suggested 50 megapixels, admin-adjustable) and let Pillow's decompression-bomb check raise rather than warn. Pillow's own default only warns at its limit and errors at twice that limit (from memory).
  • Text files: UTF-8 decoding must succeed, no NUL bytes, line count and size limits; served as text/plain; charset=utf-8. Markdown uploads are plain downloads, not rendered pages.
  • Serving: every media response carries X-Content-Type-Options: nosniff; non-media downloads add Content-Disposition: attachment. Add Content-Security-Policy: sandbox on the media location so even a misclassified file cannot run script on the site's origin. An optional media_base_url setting lets the owner serve media from a cookieless domain; it is not required for 1.0 because served files are re-encoded.
  • Quotas: per-user upload rate (RES.12) and an admin-set total storage quota per user, so one account cannot fill the disk.
  • Apache and mod_wsgi limits: the example vhost's global LimitRequestBody 10485760 would block 100 MB video. Set the larger limit only inside the upload route's <Location>. Slow uploads of 100 MB also need generous socket-timeout on the daemon process and Apache Timeout/RequestReadTimeout values; test with a throttled upload in FND.6 (not tested here).
