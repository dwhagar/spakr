RES.33: Required system components

Research thread "Research: required system components", 2026-10-21. Owner brief: list the broad things the software needs in order to be operational (a database, login and logout, and so on), find the best way to describe them, and rank them with security first and efficiency second. Product shape: a specialised wiki with some WordPress-like parts: editable static pages, and database pages whose structured fields form an infobox (with an image) while the page text is stored separately.

Recommendation

  1. Describe components with a catalogue, drawn at the "container" zoom of the C4 model and one level below. One table per area, one row per component, the same seven columns every time: ID, what the system needs (written as a requirement), what it needs from other components, security notes, security rank, efficiency note, and status with the TODO ids. This page is that catalogue (68 components).
  2. Rank every component S1 to S4 for security (definitions below). A review can then spend its time in order, and the TODO thread can schedule S1 work before anything cosmetic.
  3. Use the OWASP ASVS topic list as a completeness check, not as the format. It is the cheapest way to notice a missing component (it found MFA, session management, the Host header, vulnerability scanning and security.txt below).
  4. Keep the TODO list as the tracker. The catalogue says what must exist; TODO.md says who builds it and when. Each catalogue row names its TODO ids, and the rows marked G are the ones that have none yet.

Result of the check: of 68 components, 5 are built or started in code, 48 are planned with TODO ids, 8 are only partly covered, 5 have no TODO item at all, and 2 are deliberate omissions. 19 components contain at least one missing piece (the "G:" notes in the status column). The plan is sound; the gaps are mostly the security details that fall between the big features (listed in Gaps and changes).

Trust boundaries worth naming, because most S1 controls sit on one: (1) browser to Apache; (2) uploaded and typed content into the renderers and media tools; (3) web process to worker (a compromised worker should not reach the config secrets it does not need); (4) app to the outside world (only the SMTP relay and the optional off-host copy command).

How the components are ranked

RankMeaningCount
S1Critical. A flaw can take over an account, expose GM-only or private data, run attacker code, or destroy the source of truth.24
S2High. A flaw weakens an S1 control or gives a second route to the same harm.23
S3Medium. Information leak, availability, or hygiene.18
S4Low. Useful, but nothing breaks if it comes late.3

Order of attention (top of the S1 list)

  1. Output safety and CSP (SEC-1, SEC-2): content written by editors is shown to everyone, so XSS in a wiki reaches admins.
  2. Authorisation and visibility (ACC-7, ACC-8): one central check and one central filter; GM-only leaks through search, backlinks, history, feeds, thumbnails and downloads.
  3. Sessions, CSRF, login throttling (ACC-2 to ACC-4).
  4. Account recovery paths (ACC-5, ACC-6, and email change in ACC-11): the usual way around a strong password.
  5. Upload and media toolchain (SEC-6, MED-1, MED-2): parsers of untrusted files.
  6. Secrets, database privileges and the audit log (SEC-8, PLT-3, PLT-4, ACC-13).
  7. Source-of-truth integrity and backups (STO-1, STO-4): security includes not losing the data.

Efficiency in one paragraph

The efficiency pattern is the same everywhere and already chosen: do heavy work once and keep the result. Pages render once per content version and are cached by content key (no invalidation); the MySQL index and search tables are rebuildable copies so reads never touch git; media and mail work run in queue tasks, never in a web request; Apache serves hashed static files; the costly read endpoints (search, preview) get their own rate limits, which are also a security control. Security and efficiency conflict in two places worth deciding on purpose: password hashing (slow by design, so login limits must come first) and sessions held server-side (one indexed lookup per request, in return for real logout and revocation).
