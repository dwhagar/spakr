Web UI components: editor, tables, lightbox, media, icons, fonts, search, forms, PWA

Research thread C, 2026-10-17. Part of the web layer research (RES.11, RES.21, RES.22, RES.24) and RES.23. Sizes are gzipped and were measured by bundling each package with esbuild 0.28.2, versions and licences are from the npm registry as of today (the "published" date is the registry's last-modified time).

Math display

RES.2 decides the renderer, but the front end should not carry a math library: the server emits MathML. The prototype renders inline MathML with no script and no font (modern Chromium draws it with system math fonts). KaTeX 0.19.0 (MIT, 2026-10-01) can output MathML only (4 MB unpacked, mostly fonts the MathML-only mode does not need); MathJax 4.1.3 (Apache-2.0, 20 MB unpacked) is heavier. Risk: old TV engines (see devices). The preview endpoint uses the same renderer, so math in the editor preview needs no client code either.

Tables and data grids

  • Rendered tables (UI.14): the renderer wraps every table in <div class="table-wrap" role="region" aria-labelledby tabindex="0"> (the sanitiser allowlist must permit caption, th scope), CSS gives sticky header, borders, and inner scroll. Done in the prototype, axe clean at 280 px.
  • Admin lists and result tables: plain tables fed by the API with server-side paging and sorting; sort links are real links (?sort=name), so they work without JavaScript and are indexable where wanted.
  • Data-grid libraries evaluated and rejected: Tabulator 6.6.1 (MIT, 29.8 MB unpacked, large and inline-style heavy, not tested), Grid.js 6.2.0 (MIT, last published 2024-03), Simple-DataTables 10.3.0 (LGPL-3.0, avoid the licence in an MIT project), TanStack Table 9.3.1 (MIT, headless, needs a framework adapter). Datasets here are paged by the server, so a client-side grid adds nothing.

Fonts

  • 1.0: system font stack (system-ui, ...): zero bytes, instant text, no layout shift, no licence files, matches each platform (including TVs). The screenshots in the prototype show the sandbox's fallback face, so appearance will differ per device.
  • Optional later: a self-hosted variable font as an admin setting: Atkinson Hyperlegible Next (OFL-1.1, 34 KB woff2 for the Latin upright variable file, 38 KB italic; @fontsource-variable 5.3.0 package) is designed for legibility and fits a reference site; Inter variable is 48 KB. Rules: Latin subset only, font-display: swap, size-adjust fallback to avoid shifts, the OFL text shipped with the files. Never Google Fonts or any CDN (privacy and CSP).

Search UI (UI.6, SEARCH.7)

  • The search form is a normal GET /search?q= page rendered by the server (works without JavaScript, results are links, facets are checkbox or link filters in <details> groups that open on wide screens); this matches the server-rendered reading rule and gives bookmarkable searches.
  • Enhancement: ARIA 1.2 combobox with a listbox of suggestions from the autocomplete endpoint (SEARCH.7), roving with arrow keys, aria-activedescendant, a polite live region announcing the count (WCAG 4.1.3). About 100 lines of our own code. The same widget serves the link picker in the editor. A libraries-only alternative (<datalist>) needs no script but its styling and screen-reader behaviour vary; keep as the fallback when the script fails.
  • Highlighted snippets from the API arrive as sanitised markup with <mark> (already allowlisted); never built from raw strings in JavaScript.

Forms and validation

  • Native controls and HTML5 constraint attributes (required, type, pattern, autocomplete tokens) for instant hints; the server (pydantic via the API) is the only authority.
  • One small helper turns the API's error response into: an error summary at the top (focus moves to it on submit), per-field messages linked with aria-describedby, and aria-invalid. This is exactly the RES.18 checklist, written once.
  • Type-specific entity forms (ENT.13) are generated from the per-type schemas the API serves: rendered by the server into HTML at the edit URL (so the page loads usable) and submitted by script to the JSON API. A client-side generic form renderer is not needed.
  • No form library (Zod, vee-validate, FormKit and so on): they add a build step and duplicate server rules.

Offline and PWA: worth it?

  • Web app manifest: yes, cheap. A manifest and icons let phones and some TV launchers install the site as an app; no script, no storage. Under the CSP, manifest-src 'self'. Low priority, a few hours of work.
  • Service worker with offline reading: not in 1.0. A real benefit exists (a GM at a table with poor Wi-Fi) but the site has per-user visibility (GM-only pages, VIS.1): an offline cache that outlives logout or sits on a shared device would leak them. If built later, the rules are: cache only static assets plus public pages the user explicitly saves; never cache responses carrying Cache-Control: private or any GM-only page; purge the cache on logout; send Clear-Site-Data on logout where supported; version the worker with the asset hash. worker-src 'self' in the CSP.
  • Push notifications, background sync: not wanted.
