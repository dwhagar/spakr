RES.11, RES.21, RES.22, RES.24: the web layer

Research thread C, 2026-10-17. Decides the front-end approach (RES.11), CSS and design system (RES.21), whether Node.js is justified (RES.22) and the component approach (RES.24). Companion pages: devices, TV and foldables (RES.23) and components: editor, tables, lightbox, media, icons, fonts, search, forms, PWA. A working prototype backs the numbers.

Recommendation

  1. No Node.js in the product. Not at runtime, not at install, not in the build. Asset tooling is three small Python scripts (hashing, icon sprite, contrast check) that were written and run for this research. Node stays optional for contributors who want it (for example to run esbuild), never required.
  2. Plain modern CSS with design tokens, hand written, about 4 KB gzipped for the whole prototype. No CSS framework. Light and dark come from the same tokens, with a server-stored user choice.
  3. No-build vanilla JavaScript: native ES modules and a few small custom elements, one entry module per page, progressive enhancement over server-rendered pages. About 2 KB gzipped in the prototype (theme and TV toggles, lightbox, editor tabs, remote-control navigation).
  4. Reserve, do not adopt, a library: if the admin and editor screens outgrow plain modules, add Preact 11 with htm (about 5 KB gzipped, no JSX build step) for those screens only. Decide when UI.4 or UI.7 actually hurt, not before.
  5. Strict CSP is the design constraint and it rules out most of the popular choices (see the table). The prototype was served with default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; media-src 'self'; font-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none' and produced zero violations in 36 page loads.

Pages: a reading page (title, tags, notice, MathML, figure with lightbox, scrolling table, code, audio and video, card grid, facts sidebar) and an editor page (Write and Preview tabs that become side by side on wide screens, toolbar, form). RES.22: is Node.js justified?

No. What Node would buy us here is bundling, minifying and hashing, and none is needed:

JobWithout NodeEvidence
BundlingNot needed. Native ES modules, a handful of small files, HTTP/2 from Apache. Modules are shipped as written.The prototype's JS is 5 KB across three files.
MinifyingNot needed at this size. Apache mod_deflate (or brotli) does the work.CSS: 4.1 KB gzipped as written versus 3.2 KB minified; JS: 2.0 versus 1.2 KB (esbuild 0.28.2, measured). Under 1 KB saved per page load; revisit above about 50 KB of JS.
Asset hashing for immutable cachingtools/hash-assets.py (about 40 lines, stdlib only): renames each file to name.<sha256-10>.ext, rewrites relative import specifiers, writes manifest.json for the Jinja templates. Limits: no import cycles; imports must be static relative paths (no import maps, which need an inline script or a nonce).Run on the prototype: 6 files hashed, modules loaded from the hashed copies under the strict CSP with no errors.
Icon spritetools/make-icons.py: 19 Lucide icons copied into one SVG sprite, 3.8 KB (1.1 KB gzipped).Measured.
CSS processing (prefixes, nesting, imports)None needed: modern CSS shipped as written; no preprocessor.Browser targets below.
Test toolingPython playwright (pip, Apache-2.0; version 1.64.0 downloaded here) and a vendored copy of axe-core's single file axe.min.js (MPL-2.0, 4.14.0) injected into the page; axe-playwright-python 0.1.8 exists as a wrapper. The same checks used in this research.pip download worked; the CI runner side is not tested.

Cost of adding Node anyway

  • Ubuntu 24.04 does not ship a usable Node. Current build tools demand a recent Node: Vite 8.3.4 requires ^20.19.0 || >=22.12.0 and Tailwind 4.3.3 the same (npm registry). The Ubuntu 24.04 archive package is, from memory, Node 18, which is end of life; I could not confirm the current figure (packages.ubuntu.com returned 503). So Node would need a third-party repository (NodeSource), nvm or a container: a new apt source, a new thing to patch, on a box whose whole job is Apache plus Python.
  • Node 24 is the active LTS line until April 2028, Node 22 reaches end of life in April 2027 and Node 26 becomes LTS in October 2026 (from endoflife.date and Node release pages as returned by search; not fetched directly). A build chain pinned to Node means a forced upgrade inside 1.0's support window.
  • Supply chain: a typical Vite or Tailwind install pulls hundreds of transitive packages (not counted here), each a chance for a malicious release, in the CI that also holds repository credentials. Our Python side is already a hashed lock file (RES.15); the front end can stay as small.
  • Admins installing from source would need Node and npm install to get a working site. With no build step, the repository's static/ directory is the deliverable.

When to revisit

Adopt a Node build step (esbuild alone, a static binary, as a dev-time option) only if one of these becomes true: the editor moves to CodeMirror (needs bundling: about 175 KB gzipped for a minimal Markdown editor, measured), JS on reading pages exceeds 50 KB, or we adopt a framework with JSX or single-file components. Even then the built output is committed or built in CI, so installing the site still needs no Node.

Structure that follows

  • Real pages, no client router. Every screen is a server-rendered URL; the browser handles navigation, back, history and focus. This also satisfies the accessibility rule about moving focus on route changes (RES.18) because there is no client routing. Optional later: @view-transition in CSS for smooth navigation (Chromium-only, harmless elsewhere; support not verified here).
  • One entry module per page, loaded as <script type="module" src="..."> from the hashed manifest. Heavy modules (a future CodeMirror) are loaded with dynamic import() only on the editor page.
  • API client: one 40-line module wrapping fetch: same-origin, session cookie, the CSRF token header, the API error format mapped to field errors. No client-side validation library: HTML5 attributes give instant hints, the server (pydantic) is the authority.
  • State: per screen, in the DOM and a few module variables. Drafts of unsent edits go to localStorage (the accessibility page already requires this).
  • Without JavaScript: reading, browsing, search results, history and the facts sidebar all work. Editing, uploads and admin screens require JavaScript (they call the JSON API). Sign-in would need an extra form-encoded path on the API to work without JavaScript; I propose not supporting that in 1.0 (open question, below).

CSS rules adopted (from what failed or passed in the prototype)

  • Theme tokens as custom properties. Light is the default; dark is applied by prefers-color-scheme unless the user chose light, and by [data-theme=dark] when the user chose dark. The server renders the attribute from the account setting or a cookie, so there is no flash and no inline script (UI.12). I did not use light-dark(): it is newer (Chrome 123, from memory) and TV engines are older. The price is that the dark palette appears twice; tools/contrast.py fails the build when the two copies differ.
  • No @layer, no CSS nesting, no light-dark(). A browser that does not understand @layer drops the whole block, which on an older TV engine means an unstyled site. Container queries are used only as a progressive enhancement (the infobox) with a working single-column fallback.
  • Browser support policy: features must be Baseline widely available (web.dev: the 30-month rule) or have a safe fallback. Checked by search: :has() was newly available in December 2023, container size queries in February 2023 and CSS nesting in August 2023 (web.dev reported :has() as widely available from June 2026). The other 30-month dates are my own arithmetic; confirm on web.dev/baseline before relying on a specific feature. I could not confirm a Baseline status for light-dark(), popover or dialog from search.
  • Under the strict CSP I tested in Chromium 141: el.style.color = ..., el.style.setProperty('--w', ...) and adoptedStyleSheets all work; setAttribute('style', ...) and innerHTML containing a style attribute are blocked (2 violations logged). Consequences: dynamic sizing goes through custom properties set from JS; the HTML sanitiser (RND.3) must strip style attributes, which it should anyway; templates carry no inline style.
  • Sizes in rem, spacing in logical properties, fluid type with clamp(). TV mode simply raises the root font size, so every size follows.

Supply-chain rules to adopt: every third-party file is copied into static/vendor/ with its exact version, SHA-256 and licence recorded in a THIRD-PARTY.md file (ISC and MIT licences require keeping the notice); no package is loaded from a CDN; updates are deliberate commits. With a no-build front end this list will be short: icons (Lucide, ISC), optionally a font (OFL-1.1) and, later, one editor or player.

Performance budgets

Proposed and enforced by a small Playwright check in the daily CI run (it measures transferred sizes and fails on a breach), with the Core Web Vitals "good" thresholds as targets for a mid-range phone on a slow connection (LCP at most 2.5 s, INP at most 200 ms, CLS at most 0.1; thresholds from Google's published guidance as I know it, not re-fetched).

Decisions for the owner

  1. Node.js: (A, recommended) none anywhere in the product; (B) build-time only, adopted when the editor moves to CodeMirror. Recommendation A: the numbers above show no saving worth a new apt source and a large dependency tree.
  2. Editor in 1.0: (A, recommended) plain textarea with a small toolbar and server-rendered preview; (B) CodeMirror 6 with syntax colouring, about 175 KB gzipped and a CSP nonce. See the components page.
  3. Sign-in without JavaScript: (A, recommended) not supported in 1.0; (B) add a form-encoded login path to the API.
