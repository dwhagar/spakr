RES.16: Apache hosting: mod_wsgi, proxy and CGI

Research thread B, 2026-10-17. Unblocks FND.3 and FND.6; informs DOC.3.

Recommendation

  • mod_wsgi from apt, daemon mode, running the Flask app as its own user with a virtualenv (as the example vhost already sketches). Add WSGIApplicationGroup %{GLOBAL} and, essential for API keys, WSGIPassAuthorization On.
  • Gunicorn behind mod_proxy is a documented alternative, not part of 1.0.
  • CGI is kept for a very small set of scripts whose value is independence from the main app (a health probe, a maintenance page). It adds no capability, so do not grow it.

Experiment (real, on Ubuntu 24.04)

The research environment is Ubuntu 24.04.5. I installed apache2 2.4.58-1ubuntu8.17 and libapache2-mod-wsgi-py3 5.0.0-1build2 from the archive, created a virtualenv with /usr/bin/python3.12 and installed Flask 3.1.3, pydantic 2.14.1 (pydantic-core 2.50.1) and argon2-cffi 25.1.0. A tiny app that builds a pydantic model and an Argon2 hash was served on a local port through WSGIDaemonProcess ... python-home=<venv>.

QuestionResult
Does Flask with pydantic v2 and argon2-cffi (a Rust/PyO3 extension and a cffi extension) run under apt mod_wsgi in a venv?Yes. Two requests in sequence returned HTTP 200 with Python 3.12.3, both with the default per-vhost sub-interpreter and with WSGIApplicationGroup %{GLOBAL}. I saw no import problem in either mode.
Does the app see an Authorization: Bearer header by default?No. By default the header arrived as null. With WSGIPassAuthorization On the app received Bearer abc123. Without that directive every API-key request would be anonymous.
What is request.remote_addr with a direct client?The client's address (127.0.0.1 for the test), so no proxy handling is needed unless the owner puts a proxy in front (RES.12).
What went wrong first?Python failed at start with No module named 'encodings' because the daemon user could not read the path to the virtualenv (a parent directory was not traversable). The venv and its parents must be readable by the daemon user. A second pitfall: Apache refuses to run as root, so tests ran as www-data; production uses a dedicated spakr user.

Why I still recommend %{GLOBAL} although the default mode worked: sub-interpreters can load extension modules once per interpreter and some C and Rust extensions assume a single main interpreter. That is widely given mod_wsgi advice, from my own knowledge; I did not reproduce a failure, so treat it as a precaution that costs nothing because the daemon group hosts only this one application.

No benchmark was run; at this scale throughput is not the deciding factor.

Starting daemon settings for FND.6

WSGIDaemonProcess spakr user=spakr group=spakr processes=2 threads=8 \
    python-home=/srv/spakr/venv python-path=/srv/spakr/src \
    display-name=%{GROUP} maximum-requests=5000 graceful-timeout=20 \
    request-timeout=300 socket-timeout=120
WSGIProcessGroup spakr
WSGIApplicationGroup %{GLOBAL}
WSGIPassAuthorization On

The first five options come from the example vhost and the directive tests above. maximum-requests, request-timeout and socket-timeout values are my starting suggestions from general mod_wsgi practice and were not tested; the timeouts must cover a 100 MB video upload on a slow link (RES.9). Reload the code without restarting Apache with touch /srv/spakr/src/html/wsgi.py (standard mod_wsgi daemon behaviour).

Other vhost points

  • Upload limit: the example's global LimitRequestBody 10485760 blocks 100 MB video; set the larger limit in the upload route's <Location> only.
  • Static and media: Apache serves static/ and the published media tree directly with long Cache-Control (paths contain hashes). The private originals and quarantine trees have no Alias and sit outside the document root.
  • Protocols: enable h2 with the event MPM (Protocols h2 http/1.1); mod_deflate for text.
  • Security headers: the application sets them for dynamic responses so that tests cover them (RND.4); the vhost sets nosniff, HSTS and the strict CSP for static files.
  • Denied paths: .git and *.json are denied in the example already; config.json lives outside the document root anyway (RES.20).
  • TLS certificates: certbot (2.9.0 on 24.04) with the Apache plugin, or Apache's built-in mod_md; the install guide picks one (not researched further).

CGI: what stays

  • With the event MPM (Ubuntu's default) CGI runs through mod_cgid; confirm the module is enabled in FND.6.
  • Each CGI request starts a new Python process (tens of milliseconds), fine for rare calls, wrong for anything busy.
  • Python 3.13 removed the standard cgi and cgitb modules (PEP 594), so the scripts must not import them; they only print headers and a body. This matters for 26.04 (Python 3.14).
  • Candidates worth keeping as CGI: health.py (checks MySQL, Redis, queue depth, disk, without loading Flask, so monitoring works even when the app is broken) and maintenance.py (static "upgrade in progress" answer, used by the upgrade script). Everything else belongs in the Flask app.

What I could not verify

  • mod_wsgi 5.0.2 with Python 3.14 on 26.04 (not installed).
  • The suggested timeout and maximum-requests values, behaviour under load, and the failure mode of sub-interpreters with PyO3 modules (not reproduced).
  • Python 3.12 only; the test environment's default python3 was a newer interpreter, so the venv was built explicitly from python3.12.
