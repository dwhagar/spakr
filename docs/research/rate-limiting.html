RES.12: Rate limiting

Research thread B, 2026-10-17. Unblocks OPS.2 and the throttling parts of AUTH.2, AUTH.5 and MED.1.

Recommendation

  • Use Flask-Limiter (4.1.1) with the Redis backend. Do not write own counters.
  • Limit by the strongest identity available: API key, else signed-in user, else client IP. Login and reset have additional per-account limits.
  • Throttle, never lock out: failed logins slow down exponentially, an attacker cannot lock a victim out of their account.
  • Defaults live in the settings registry (CFG.2) and are admin-adjustable; the limits table below is the starting set.
  • Keep the client-IP rule simple and explicit: use the socket address unless the owner declares trusted proxies.

Signed-in users and keys get limits separate from the anonymous ones, so a busy IP (a shared network) does not throttle signed-in editors. These numbers are my starting values for a small community site, not measured.

Behaviour

  • Response: HTTP 429 in the API's standard error format (see RES.14) with a Retry-After header. Also send the standard rate-limit headers (headers_enabled) so the JavaScript client can back off.
  • Redis unavailable: Flask-Limiter offers an in-memory fallback. Use it (fail open per process) for reads and writes, but keep login and reset fail closed for the per-account limits: if Redis is down, throttling defers to the slow Argon2 hash plus the per-process semaphore from RES.5. Document this in the install guide. (Fail-open versus fail-closed is a policy choice; the library options exist as inspected, exact semantics to confirm in OPS.2.)
  • Storage: Redis database separate from the RQ queue database (redis.db in the config example is for RQ; use db + 1 for limits and cache) so a queue flush never resets limits and vice versa.
  • Admin exemptions: a configurable allow-list of IPs (monitoring) is exempt from read limits.
  • Audit: a burst of 429s on login for one account is logged once per window, not once per request.

Client IP behind Apache

  • With mod_wsgi directly behind Apache (the recommended hosting, RES.16) the socket address is the real client, and request.remote_addr is correct (confirmed in the hosting test: the app saw 127.0.0.1 for a local client).
  • If the site sits behind a CDN or reverse proxy, enable Apache's mod_remoteip with the proxy's address ranges declared as trusted (RemoteIPInternalProxy, RemoteIPHeader). Never trust X-Forwarded-For from arbitrary clients: it is spoofable, and a spoofed value would both evade limits and poison audit logs.
  • A config option site.trusted_proxy_count (default 0) feeds Werkzeug's ProxyFix only when the owner sets it.

What I could not verify

  • Flask-Limiter documentation text and header names (docs sites unreachable); behaviour was confirmed only from the installed package's constructor options.
  • Whether the starting numbers fit real use; they are meant to be tuned after launch from the 429 counts.
