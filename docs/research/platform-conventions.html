Platform conventions: queue, logging, MySQL, outbound HTTP, testing and CI, privacy

Research thread B, 2026-10-17. Cross-cutting findings that do not have their own RES item. Each section names the TODO items it affects. Related pages: auth, settings, hosting, packaging.

1. Task queue (QUE.1 to QUE.4)

Rule: the database is the ledger, Redis is the doorbell. Every background job has a database row recording the desired outcome (media.state, email_outbox.state, a reindex job row). Redis only carries the wake-up. If Redis loses its data, spakr requeue-stuck re-enqueues rows still marked queued or processing, so no backup of Redis is needed.

  • Library: RQ 2.12.0 (BSD-2) with redis-py (current 8.1.0; the apt versions are old, see RES.15). RQ runs each job in a forked process, which suits ffmpeg and ImageMagick children and isolates crashes.
  • Queues: default (cache warm, index jobs), mail (single worker, serial sending), media (long jobs, concurrency set by the admin). One systemd template unit spakr-worker@<queue>.service per queue, running as spakr with sandbox options (NoNewPrivileges, ProtectSystem=strict with ReadWritePaths for the data directories, PrivateTmp); the media worker additionally gets no network (PrivateNetwork=yes is possible because ffmpeg and ImageMagick need none).
  • Timeouts and retries: per-kind job_timeout (mail 60 s, image 120 s, video set from duration limits); retry only for transient errors (email page); short result_ttl and a longer failure_ttl so the admin can inspect failures (QUE.3's status API reads RQ registries plus the database row).
  • Redis security: Ubuntu's package binds to loopback; keep it that way, set requirepass (the redis_password secret already in the config example), keep protected mode on. Databases: db for RQ, db+1 for rate limits and caches (RES.12).
  • Licence note (from memory): Redis 8 added AGPLv3 as a licence option; Ubuntu 24.04 ships 7.0.15 (the older BSD licence) and 26.04 ships 8.0.5. spakr only talks to Redis over a socket, so this does not affect spakr's own licence.

2. Logging (FND.8)

  • Standard library logging with a small JSON formatter (or python-json-logger 4.2.0, BSD-2) instead of a logging framework; structlog 26.1.0 (MIT or Apache-2.0) is an option if structured context becomes heavy, but is not needed for 1.0.
  • Web app logs go to stderr, which mod_wsgi writes into the Apache error log; workers log to journald. One request id (generated if absent, returned as X-Request-ID and in error bodies) ties access, app, audit and error output together.
  • Never log passwords, tokens, API keys, session cookies, the Authorization header, request bodies of auth and settings routes, or secret settings (Secret type). A test feeds known secrets through the stack and greps captured logs.
  • Access logs: tokens are never in URLs (fragment links, RES.5), so Apache's default access log does not capture them; query strings are not logged for the settings and auth routes in any case.
  • Rotation: Ubuntu's logrotate configuration for Apache covers the Apache logs; the app adds nothing of its own.

3. MySQL access layer and migrations (DB.1, DB.2)

  • Target: Oracle MySQL 8.0 (Ubuntu 24.04, security builds up to 8.0.46 in the archive listing) and 8.4 (Ubuntu 26.04). MariaDB is not a target: collations, JSON and full-text behaviour differ and the plan uses MySQL's ngram parser option.
  • Driver and ORM: mysql+pymysql://, SQLAlchemy 2.0.x, Alembic 1.20.0 (RES.15). Connect with charset=utf8mb4; create the schema with utf8mb4 and an accent-insensitive collation such as utf8mb4_0900_ai_ci (MySQL 8 default) after the full-text search research (RES.7) confirms it; InnoDB only.
  • Pool: pool_pre_ping=True; pool_recycle below the server's wait_timeout; pool_size about 8 per process (2 processes by 8 threads in the example vhost) so the worst case stays under MySQL's default 151 connections together with the workers.
  • Unix socket option: allow database.socket in config.json as an alternative to host and port (faster, no TCP exposure).
  • MySQL DDL is not transactional: each CREATE/ALTER commits implicitly, so a failed migration can leave a half-applied change that Alembic cannot roll back. Rules: one logical change per migration, guard re-runnable steps, take a backup before spakr db upgrade (it is in the upgrade procedure), and test every migration from the previous schema in CI, not only from empty. alembic check (compare models with migrations) runs in the daily job (command recalled from Alembic; confirm at DB.2).
  • Privileges: the application account gets privileges on its own schema only; no FILE, SUPER or global rights. Optional hardening: INSERT/SELECT only on audit_log (retention purge via the CLI with the migration account).
  • Write ordering with git: commit to git first, then update the index rows in one transaction; if the second step fails, the index is stale but the content is safe and spakr reindex repairs it. This is the order the "git is the source of truth" decision implies.
  • Time: store all timestamps in UTC; the UI formats them.

4. Outbound HTTP and the User-Agent helper (FND.4, REL.5)

  • One module sends every outbound request. The plan's header format is valid under RFC 9110's grammar (product tokens, then a comment): spakr/1.2.3 spakr-api/1 (+https://site/contact). The contact URL must not contain parentheses or unescaped characters; the helper percent-encodes it.
  • Today's callers: none required by the plan; likely only the optional Pwned Passwords check and future link checks or webhooks. Use the standard library urllib.request unless a real need for sessions or HTTP/2 appears (requests 2.34.2, Apache-2.0, and httpx 0.28.1, BSD-3, were considered and not needed).
  • Safe fetch rules (so admin-supplied URLs cannot reach internal services): https only unless an admin allows plain HTTP for a named host; resolve the host and refuse loopback, private, link-local and cloud-metadata addresses (for example 169.254.169.254) and re-check after each redirect; at most 3 redirects; connect timeout 5 s, read timeout 15 s; response size cap; no cookies; never forward credentials across hosts.
  • Version string: read from the generated _version.py (RES.15) and the API version constant; a test asserts the format with a regular expression.

5. Testing and CI under the daily-only schedule (FND.7, TST.1, TST.2)

Standing preference: code tests run only daily at 07:00 UTC and by manual dispatch, never on push or pull request unless asked. The strategy keeps that and shortens the feedback loop another way.

  • User data export: an account page action that returns the user's profile, their contributions list and audit entries about them as JSON. Small, valuable, and cheap once the API exists; suggested as a new item (AUTH.12).

  • Public content: pages are public by default and licensed CC BY-SA, so authors must understand that edits are attributed under their username; the edit screen says so (UI.9).
