RES.32: Calm, responsive UX (Mastodon and Wiki.js style)

Research thread "Research: calm responsive UX", 2026-10-21. Builds on the web layer research (RES.11, 21, 22, 24, RES.23, components) and RES.18; it does not repeat them. Owner brief: modern, calm, simple like Mastodon and Wiki.js, built mobile-first from the ground up, open source icon packs, an interface that gets out of the way.

Recommendation

The earlier research already chose the right engine for a calm UI: server-rendered pages, hand-written modern CSS with tokens, no-build ES modules, strict CSP, system fonts, a Lucide sprite. Keep all of it. What was missing was the design rules that make it feel calm, and a few decisions the shell plan (UX.1 to UX.28) needs. This page adds:

  1. Ten calm rules (below) written as testable statements, so "gets out of the way" is something a review can check.
  2. One content column, two optional rails. Reading width is capped (about 70ch), the left drawer and right rail appear only when there is room, and nothing else competes for attention. This is the Mastodon single-column and Wikipedia Vector 2022 pattern, and it matches the already planned shell.
  3. Per-setting themes change colour and heading character only, never layout. Three settings times light and dark gives six generated, contrast-checked palettes (UX.29).
  4. Icons: stay with Lucide (ISC, with an MIT part). Licence details and the runners-up are below; THIRD-PARTY.md must carry both Lucide notices.
  5. Progressive enhancement is a rule per component: each interactive part has a working no-JavaScript form (UX.30).
  6. The editor stays a textarea, but typed fields live in a real form above the body and the toolbar is built for phone keyboards (UI.24).
  7. No JavaScript framework, no CSS framework. The case for Preact stays "reserved, decide when UI.4 or UI.7 hurt".

Ten calm rules

These become part of the UI acceptance checklist (UI.13). Each is checkable in the Playwright screenshot run (UX.12) or a code review.

  1. Content first. On a phone the first screen after the top bar shows the page title and the start of the text. Rails, tools and metadata are one tap away, never above the text.
  2. One accent colour per setting, used for links, the current item and primary buttons only. Everything else is neutral. Status uses text and an icon as well as colour.
  3. One primary action per screen (Save, Edit, Search). Secondary actions are plain buttons or links; destructive ones are never the default.
  4. Quiet motion. Transitions of 120 to 200 ms for the drawer and disclosure, nothing that moves on its own, all of it off under prefers-reduced-motion.
  5. No surprise layers. No pop-ups, auto-playing media, carousels, cookie banners (only functional cookies are set) or infinite scroll. Lists use pagination so the back button and keyboard work.
  6. Messages stay put. Success is a short polite status line; errors stay on screen next to the field and in a summary until fixed. No toasts that vanish.
  7. Whitespace is a feature. Spacing comes from the fluid space token; one reading width; borders are hairlines or none; elevation only on overlays (drawer, dialog, combobox list).
  8. Label first, icon second. Navigation and primary buttons carry text. Icon-only buttons (hamburger, theme, close) have an accessible name and a visible focus ring, and are 44 px on touch.
  9. Same place every time. The shell never rearranges between pages; page actions sit in the same spot for every entity type (WCAG 3.2.3, 3.2.6).
  10. Fast by default. A reading page needs no script to be complete and stays inside the budgets below.

Layout, navigation and search

  • Shell. Keep the planned top bar, left drawer (site contents), right rail (page TOC, actions, related). Use named CSS grid areas so the same markup becomes one, two or three columns. Under 62rem the rail collapses to a <details> block under the title; the drawer is an overlay.
  • Phone navigation. The top-bar hamburger decided in UX.1 is enough for a reading-first site. A bottom tab bar (the Mastodon app's choice) helps feed-style apps where you switch views often; a wiki is read far more than navigated, and a bottom bar costs screen height and clashes with the editor keyboard. Not recommended; offered as an owner decision (see Questions).
  • Drawer content. Sections by entity type, then setting, plus the admin-editable links (UX.16). Collapsible groups are <details> with the group containing the current page open. Show at most two levels; deeper browsing is the Browse page.
  • Search. Always in the top bar on wide screens, one icon on narrow ones that opens the field full width (UX.23). Results group by entity type, show the setting as a text badge, a short snippet with the match, and the type icon. Arrow keys and Enter work in the combobox; a plain results page is the no-JS path (already planned in UI.19). Empty state offers "create this page" to editors. Pressing / to focus search is convenient but is a single-key shortcut (WCAG 2.1.4): ship it only with an off switch in user settings, default off.
  • Links between entries. Inline entity links get the type icon in front of the name; missing pages show a dashed underline and the word "(missing)" for assistive tech, not red alone. Hover previews (as Wikipedia has) are not needed and are bad on touch; skip for 1.0.
  • Breadcrumbs above the title (UX.17); the page TOC follows the reader with scroll-spy (UX.13). Use scroll-padding-top equal to the sticky bar so focused and anchored items are never hidden (WCAG 2.4.11).
  • Infobox ("facts"). For a game database the stat block is the most-read element. Render it as a definition list: in the right rail on wide screens, at the top of the article under the title on phones, collapsed after the first rows if long. The container query already prototyped (label/value side by side only when wide enough) is the right tool.

Design tokens and per-setting themes

Tokens already exist (UI.12, UX.2). Structure them in three layers, each in its own CSS file or block, so a theme change never touches components:

LayerContainsChanges by
PrimitiveNeutral ramp, space and type scales, radii, shell sizes.Almost never
Semantic--surface, --text, --text-muted, --border, --accent, --accent-text, --focus, status colours. Defined for light and dark.Colour scheme (user) and setting (page)
ComponentOptional local tokens such as --card-bg: var(--surface-raised).Component authors

Setting themes. The page's setting sets data-setting="fantasy|horror|scifi" on <body> (server-rendered, no script). Only the accent, a surface tint, the heading font and the type-icon accent change. Layout, spacing and component shapes are identical in all three, so there is one UI to test and maintain. Suggested starting accents (to be tuned by eye): fantasy a warm amber or forest green, horror a muted teal or oxblood on a cooler grey, scifi a cyan or indigo. Pages with no setting (home, tools, settings) use a neutral accent.

Keeping contrast guaranteed. Do not hand-pick 24 colours. Extend the existing Python tool: give it a hue per setting and it writes the accent steps at fixed lightness and saturation for light and dark, then runs the existing WCAG pair check on all six palettes. Emit plain hex (not oklch(), which older TV engines lack). The generated file is committed, so there is no build step at install time. Accent text on the surface needs 4.5:1; the focus ring 3:1 against both.

Colour scheme (light, dark, auto) is the user's choice and independent of the setting, stored server-side as already planned (UX.9). Always set color-scheme; support forced-colors and prefers-contrast: more by falling back to system colours for borders and focus.

Typography

  • Body: system UI stack (system-ui, -apple-system, "Segoe UI", Roboto, "Helvetica Neue", Arial, sans-serif), fluid size and 70ch measure as already prototyped, line height 1.6 for prose and 1.4 for UI, font-variant-numeric: tabular-nums in stat blocks and tables. System fonts cost zero bytes and never flash.
  • Optional character: a setting may name a heading font from a short list of self-hosted OFL fonts, subsetted to Latin, WOFF2, font-display: swap, preloaded only for headings, at most two files per setting. The reading text stays on the system stack so a font failure never hurts legibility. Atkinson Hyperlegible Next (OFL 1.1, variable weights 200 to 800, reserved font names "Atkinson" and "Hyperlegible") stays the offered accessibility option for body text. Heading font suggestions are not fixed here: this needs a look at real candidates and the owner's taste. The licence needs a line in THIRD-PARTY.md (OFL requires the notice to travel with the font).
  • Scale: 1.2 ratio steps from the existing --step-* tokens; do not add more than six sizes. Headings use text-wrap: balance where supported.
  • No fake bold or letter-spaced uppercase labels as the main way to create hierarchy; use size, weight and space.

Delivery. One SVG sprite built by make-icons.py from the icons actually used, referenced with <svg><use href="/static/icons.svg#name"> (same origin, so the strict CSP is fine). Decorative icons get aria-hidden="true"; icon-only buttons get a text name. Sizes 20 px in text and 24 px in buttons, stroke from currentColor so dark mode and settings need no extra icon files. Entity-type icons (character, item, technology, place, magic, psionics, ability, skill, entity, race, nation-state, page) are a fixed mapping kept in one table (UX.32) so adding a type means adding one line.

CSS approach and keeping it maintainable

  • Files: tokens.css (primitive, semantic, setting overrides), base.css (reset, typography, forms), layout.css (shell grid), components/*.css (one file per component: drawer, rail, card, infobox, table-wrap, combobox, dialog, editor). Served as separate files over HTTP/2 or concatenated by hash-assets.py (a plain join, still no processing).
  • Naming: mostly element selectors for prose and forms, plus short component classes (.drawer, .card, .infobox) with state in attributes ([aria-expanded="true"], [aria-current="page"]) so state styling and accessibility cannot drift apart. Specificity stays at one class; no !important, no IDs for styling. Add a small lint check in the daily run that fails on !important, style= attributes and unknown var(--) names.
  • Logical properties (margin-inline, padding-block) throughout, so a right-to-left language later costs nothing.
  • Style guide page (UX.31) rendered by the real templates showing every component in all states, in each setting, light and dark. It is both the developer reference and the page the screenshot tests use, so a visual change is reviewed in one place.
  • Budgets (proposal, checked by UI.17): reading page CSS 20 KB gzipped, JavaScript 8 KB gzipped, editor page JavaScript 20 KB, no web fonts blocking first paint, all images with width and height. The prototype is 4 KB of CSS and 2 KB of JavaScript, so there is room.

Editing experience

  • Typed fields are a form, not YAML. For a game database most of an entry is structured (stats, race, setting, relations). The editor shows a generated form for the entity's fields (RES.13 defines them), then the Markdown body textarea below. Front matter is serialised by the server; editors never see it. This is the biggest usability win for non-technical game masters.
  • Phones. Add interactive-widget=resizes-content to the viewport meta so the on-screen keyboard shrinks the layout instead of covering the field (Chromium 108 and later, from my knowledge; test on a real device). The toolbar is a horizontally scrolling row of 44 px buttons kept above the keyboard; Write/Preview are tabs (already prototyped).
  • Safety net. Draft in localStorage with a "restore draft" line, a leave-page warning only when there are unsaved changes, and the base-revision conflict shown as a normal error summary (GIT.7).
  • Shortcuts. Ctrl/Cmd+B, I, K and Ctrl+Enter to save are modifier shortcuts, allowed under WCAG 2.1.4. A short collapsible Markdown cheat sheet sits next to the toolbar.
  • Link and media picker reuses the search combobox (UI.19). Insert produces Markdown the editor can still read and change.
  • Not worth doing for 1.0: WYSIWYG, slash menus, drag-and-drop block editing, collaborative editing.

Performance

  • Server rendering and the content-keyed render cache (RES.25) make the HTML cheap; send ETag and let Apache compress (brotli if the module is present, otherwise gzip).
  • Hashed static files with immutable caching (hash-assets), page HTML revalidated.
  • width and height on every image, loading="lazy" below the fold, fetchpriority="high" on the first large image only; thumbnails from the media series via srcset.
  • Add to UX.12 a throttled-network load per key page (Playwright with Chrome DevTools network and CPU throttling) recording largest contentful paint and layout shift against a budget. This works without Node, in the same Python Playwright setup.

Anti-patterns to refuse

A CSS or JS framework; icon fonts (they fail silently and cannot be recoloured per rule); inline style= or event attributes (CSP); modal dialogs for ordinary flows; hover-only features; infinite scroll; autoplaying anything; fixed pixel font sizes; colour-only meaning; hiding content from keyboard users behind gestures (swipe-to-open drawers are an optional extra, never the only way).

Questions for the owner

  1. How far should per-setting themes go? Recommended: accent colour, surface tint and heading font only. Alternative: accent only (simplest), or a fuller restyle (more testing, risks an uneven product).
  2. Phone navigation: keep the top-bar hamburger and drawer (recommended), or add a bottom tab bar on phones (Home, Search, Browse, Menu)?

Defaults above are used until answered; both are cheap to change because they live in tokens and the shell template.

What could not be verified

No real devices, no Safari or Firefox, no screen reader; the interactive-widget viewport value, view transitions and the single-key shortcut guidance are from my own knowledge and not tested; Wiki.js and Wikipedia layout notes are impressions; game-icons.net licence not read; heading font candidates not chosen or measured.
