RES.20: Settings and secrets implementation

Research thread B, 2026-10-17. The approach is decided by the owner: every option holding a secret lives in config.json; everything is editable in the web interface except the MySQL credentials; the app rewrites config.json atomically at mode 0600; secret fields are write-only. This page confirms the implementation details. Unblocks CFG.1 to CFG.7, FND.2, AUTH.8, MAIL.3.

Recommendation

  • One settings registry in code (CFG.2) defines every option once. The loader, the admin API, the web forms, the validation, and examples/config.json.example are all generated from it; a CI check fails if the committed example differs from the generated one.
  • Each option lives in exactly one place: secrets and the manual-only database block in config.json; every other web-editable option in the config database table (CFG.4). No option is stored twice, so there is no precedence puzzle.
  • Rewrite config.json with a lock file, a temporary file in the same directory, fsync and os.replace. Keep the database block untouched byte-for-value, and refuse writes to it.
  • Reload across workers by checking the file's identity (inode, size, modification time) at most once a second.

Tested: atomic rewrite under contention

A proof of concept implemented exactly the write procedure below and ran it with 4 writer processes (50 read-modify-write updates each, different keys) while a fifth process read and parsed the file in a tight loop, on Ubuntu 24.04 with Python 3.13.

This proves the locking and replace logic on a local filesystem. It does not cover network filesystems (do not put config.json on NFS) or power loss (the fsync calls are there for that case but a crash was not simulated).

Write procedure (for CFG.5)

  1. Open (create if needed) config.json.lock in the same directory and take an exclusive fcntl.flock. Lock a separate file, not config.json, because os.replace changes the file's identity.
  2. While holding the lock, re-read the current file (another worker may have changed it).
  3. Apply the change to the parsed dict: only keys the registry marks web-editable and not part of database. A secret field accepts a new value or a clear; an empty submission means "unchanged", an explicit null means "clear".
  4. Validate the complete result against the registry (types, ranges, URL and host formats). On failure return the error and write nothing.
  5. Write to config.json.tmp.<pid> created with O_CREAT|O_EXCL and mode 0600; flush and os.fsync the file; os.replace over config.json; fsync the directory; release the lock.
  6. Record an audit entry naming the changed keys only (mail.password changed), never values.
  7. JSON has no comments, so the _about and _note keys in the example are data: the loader ignores keys starting with an underscore, and the writer preserves them and the key order (two-space indent, trailing newline).

Where the file lives and who owns it

  • Default path /etc/spakr/config.json, overridable with the SPAKR_CONFIG environment variable (development uses a git-ignored config.json in the checkout; .gitignore already ignores every *.json).
  • The directory must be owned and writable by the app user (spakr:spakr, mode 0750) because an atomic replace needs permission to create and rename files there; the file is 0600. The Apache www-data user needs no access: mod_wsgi daemon processes and the queue worker run as spakr.
  • Never inside the document root; the example vhost also denies *.json.
  • The loader refuses to start if the file is readable by group or others and says so (a clear startup error, as CFG.3 asks for the database credentials).
  • Hard-fail messages never print values: they name the key and the rule broken.

Reload across processes (CFG.6)

  • Each WSGI process caches the parsed file with its (st_ino, st_size, st_mtime_ns). On each request it compares with os.stat at most once per second (one syscall); on change it re-parses and re-validates.
  • If the new file is invalid (hand-edit mistake), keep the old configuration, log an error with the key name, and flag the admin settings page and the health check. Do not crash a running site.
  • The RQ worker re-checks before each job (jobs are forked per job, so a changed file is picked up naturally); the mail job therefore always uses the current relay password.
  • Non-secret settings in the database use a short (5 second) cache per process plus a version counter in Redis that the writer increments; processes poll the counter once a second. Redis outage means the TTL alone applies.
  • Options that cannot change live are marked restart_required in the registry (the paths, Redis host, the secret key if it changes the cursor-signing key); the UI shows "applies after restart".

Secrets handling

  • Write-only API: reading a secret returns {"configured": true} or false, never the value; writing sends a new value or null to clear.
  • In code: secrets are wrapped in a small Secret type whose repr and str are ***, so accidental logging or error pages cannot print them.
  • Logs and audit: request bodies of the settings endpoints are never logged; the audit detail lists key names only.
  • Secret key: secrets.secret_key is only used to sign opaque values such as pagination cursors and short-lived download links (browser sessions are random server-side tokens, RES.5). Flask 3.1 supports SECRET_KEY_FALLBACKS (found in the installed Flask 3.1.3 source), so rotation keeps old signatures valid for a while: the registry keeps an optional list secrets.secret_key_previous. Changing the key invalidates nobody's login.
  • The MySQL password: never returned or editable through the API or UI (CFG.3). Changing it means editing the file by hand and reloading the app (touch wsgi.py) and the worker.
  • Backups: the file goes into backups encrypted (RES.17).
  • Exposure test: a test requests every settings endpoint and a deliberately triggered error page and asserts that no secret value appears in any response or log line.

First-run bootstrap (FND.9)

  • spakr init-config creates config.json from the example with a freshly generated secret_key (secrets.token_urlsafe(48)) at mode 0600, prompts for the MySQL host, name, user and password, and refuses to overwrite an existing file.
  • The admin then signs in (created by spakr create-admin, AUTH.11) and fills in the rest on the settings screens, including the SMTP relay and its test message (MAIL.3).

Registry shape (for CFG.2)

Setting(key="mail.host", type=Host, default="", secret=False,
        web_editable=True, store="db", restart_required=False,
        validate=..., label="SMTP relay host", help="...")
Setting(key="secrets.mail_password", type=SecretStr, secret=True,
        web_editable=True, store="file", ...)
Setting(key="database.password", secret=True, web_editable=False, store="file")

From it: a validator, the loader's defaults, the OpenAPI schema for the settings endpoints (RES.14), the form definitions the UI renders, and the example file. Storage follows the committed example: the database, secrets, mail, redis, paths and site blocks stay together in config.json (so the relay is configured in one place, password included); options added later that are neither secret nor bootstrap data go to the database table.

What I could not verify

  • Behaviour on network filesystems or after a simulated power cut.
  • That mod_wsgi's multiple daemon processes all pick up the change within the one-second window (design, not load-tested).
