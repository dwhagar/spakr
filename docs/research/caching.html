RES.25: Caching rendered pages in memory and on disk

Research thread A, 2026-10-17. A new research item added because the brief names caching and no item covered it. Unblocks RND.5 and SEARCH.10; feeds QUE.4 and the HTTP headers in RES.8. Measurements on the same container as the other pages; Redis 7.0.15 and MySQL 8.0.46 from Ubuntu 24.04.

Recommendation

  • Cache the rendered page body, keyed by content, so nothing ever needs invalidating. Key = SHA-256 over (page id, git commit of the page content, render version, sanitiser allowlist version). An edit creates a new commit, so a new key; a code release or an allowlist change bumps a version, so a new key. Old entries are never wrong, only unused, and are removed by size.
  • Two layers: a per-process in-memory LRU, then files on disk. No Redis for rendered pages. Redis stays for what must be shared and changes constantly (the queue, rate-limit counters) as decided by thread B. This reads "memory (Redis, per-process) and disk caches" in SEARCH.10 as: per-process memory and disk; Redis is not needed for it.
  • Disk layout: cache/render/ab/cd/<key>.html (two directory levels from the key). Write to a temporary file and os.replace it into place (atomic, so a reader never sees half a file; verified pattern used for config.json in RES.20). The operating system's page cache is the shared memory cache: a warm read took 5 microseconds.
  • In-memory layer: a bounded LRU (for example cachetools.LRUCache, MIT, or a small OrderedDict) of the last 200 rendered bodies per web process (about 20 KB each, so a few MB per process). It removes even the file read for hot pages such as the home page.
  • Cache what is the same for every viewer, and nothing that depends on the user. The cached unit is the sanitised body fragment. The page shell (menus, login state, theme) is rendered fresh per request; it is cheap. A cached fragment is never shared across visibility levels because in 1.0 visibility is per page, not per block.
  • Link status is resolved after the cache, in one batch pass. Wiki links in the cached fragment are stored as plain <a class="wikilink" href="/wiki/slug">. At response time one SQL query asks which of those slugs exist and are visible to this viewer, and a regular-expression pass marks missing ones (red links) and unwraps links to GM-only pages for readers without the GM role. Measured: 33 microseconds for 60 links on a 15 KB fragment, plus one indexed query. This keeps the cache valid when a target page is created, renamed, deleted or hidden, and cannot leak a hidden page's name through the cache (VIS.3).
  • Stampedes: on a miss, take a per-key lock (an exclusive flock on cache/locks/<key-prefix>), re-check the file, render, write, release. Concurrent readers of a new page wait for one render instead of all rendering the maths.
  • Size limit and eviction: an admin setting, default 256 MB for the render cache. A scheduled queue job (QUE.4) deletes the oldest files by modification time beyond the cap. Files are tiny: the 9.7 KB sample page; 50,000 such pages would be about 0.5 GB, hence a cap, not a promise of everything cached.
  • Warm-up: after a version bump (release, allowlist approval) the queue job re-renders the most-viewed and most recently edited pages first (QUE.4); the rest render on demand.
  • HTTP caching sits on top: the same key is the page's ETag; conditional requests answer 304 without even reading the cache. Rules for Cache-Control and GM-only pages are on the SEO page. Apache's mod_cache is not recommended for 1.0: invalidation and the risk of serving a GM page from a shared cache outweigh the gain.

Measurements

Rendered sample page of 9.7 KB (the sample document repeated 10 times, Markdown then sanitised). Mean over 2,000 runs (200 for rendering).

OperationTime
In-process LRU dictionary lookup0.2 microseconds
Read a file from disk, warm in the operating system's cache5.3 microseconds
Redis GET over TCP on localhost110 microseconds
MySQL SELECT of the blob by primary key247 microseconds
Render on a miss: Markdown and sanitiser, no maths13.3 ms
Render on a miss with maths: add 20 formulasa few ms more (pure Python, 20 formulas, see RES.2)
Link status pass (60 links) after the cache33 microseconds, plus one indexed query

Every cache layer is more than 50 times cheaper than rendering, and all of them are far below the cost of the rest of a request (database, templates), so the choice among them is about simplicity, not speed. Files and memory need no extra service, survive or rebuild trivially, and make Redis outages irrelevant to page reads. The MySQL row is the worst of the four and would also bloat backups.

Other things considered for caching

CandidateDecision
Search resultsNo cache for 1.0: queries took 2 ms (5,000 pages) to 36 ms median (50,000 pages) (RES.7). If a facet-count query is slow, cache it for 60 seconds in memory.
Sitemap files and the feedGenerated files on disk, rewritten by a job after changes (RES.8).
Media variantsNot a cache: files in the hashed media directories, produced once.
API list responsesHTTP validators only (ETag); no server-side cache.
Redis as the shared cacheNot needed; adds a network hop and a failure mode. Revisit only with several web hosts.
Templates, Jinja bytecode and the sanitiser CleanerIn-process (the Cleaner is built once per allowlist version, RES.3).
Python functools.lru_cache on renderingNo: unbounded keys, per-process only, and it cannot hold the version in the key cleanly.

Items this changes

  • RND.5: key and layout above; atomic writes; per-key lock; link-status pass as part of RND.5 or LNK.1.
  • SEARCH.10: per-process LRU plus disk cache; no Redis dependency for it; size cap setting; sitemap and feed generation share the disk cache directory.
  • QUE.4: cache-prune and cache-warm jobs.
  • VIS.3: leak test for cached pages: a GM-only page title must not appear for a reader through a cached neighbour page's links.

What could not be verified

  • Behaviour under mod_wsgi with several daemon processes (the memory LRU is per process by design; the file layer is shared).
  • Disk cache behaviour on a very slow or network filesystem (single local disk assumed).
  • Real page sizes and hit rates; the sample document was synthetic. Add hit and miss counters to the admin status screen so the cap can be tuned from facts.
