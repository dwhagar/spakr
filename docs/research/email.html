RES.6: Email through an external SMTP relay

Research thread B, 2026-10-17. Unblocks MAIL.1, MAIL.2, MAIL.3. Decided earlier by the owner: external SMTP relay, never a local MTA; relay settings are configuration (secrets in config.json, the rest editable in the admin settings). The relay provider and sender address are not chosen yet, so nothing below depends on one.

Recommendation

  • Use the Python standard library: smtplib to talk to the relay and email.message.EmailMessage to build messages. No mail framework.
  • TLS: starttls on port 587 (the default, upgrade is mandatory: if the relay does not offer STARTTLS the send fails), ssl (implicit TLS) on port 465, and none only when an admin explicitly confirms the relay is on a trusted local network. Certificates are always verified with ssl.create_default_context().
  • Send from a queue job on its own mail RQ queue, with retries for temporary failures, using the existing email_outbox table as the ledger.
  • Send plain text plus a simple HTML alternative; no tracking pixels, no remote images, no links except the single action link.
  • Settings: the keys already in examples/config.json.example (mail.host, mail.port, mail.tls, mail.username, mail.sender, and the secret secrets.mail_password). Add optional mail.sender_name, mail.reply_to and mail.timeout.

Sending rules

  • Connection: port 587: SMTP(host, 587, timeout=30), ehlo(), starttls(context=ctx), ehlo(), login(user, password), send_message(), quit(). Port 465: SMTP_SSL(host, 465, context=ctx, timeout=30). The password comes from the write-only secret; it is never logged, and exception messages are scrubbed before they reach email_outbox.last_error.
  • Headers: From is the configured sender (optionally with the site name as display name, quoted by EmailMessage), Date, Message-ID from email.utils.make_msgid(domain=<sender domain>), Auto-Submitted: auto-generated (so autoresponders do not reply; RFC 3834, from memory), optional Reply-To. Subjects are fixed templates; user-supplied text only appears in the body.
  • Recipients: exactly one recipient per message; the address is validated and lower-cased when the invitation or account is created.
  • Retries: connection errors, timeouts and 4xx replies retry with growing delays (about 1, 5, 15 and 60 minutes, then give up after 5 attempts). 5xx replies (bad recipient, rejected sender, authentication refused) fail at once and set state = failed with the SMTP reply text for the admin. A failed authentication also raises a visible admin warning, because every message will fail until the password is fixed.
  • Throttle: a single worker process for the mail queue sends serially, which keeps the site under typical relay rate limits. A per-hour cap is an admin setting.
  • Tokens in the outbox: the invitation or reset token has to be in the message, so the payload holds it until the mail is sent. Clear the token field when the message is sent, when it fails permanently, and in any case when the token expires.
  • Test message: MAIL.3's "send test message" runs the same code path synchronously with a short timeout and returns the SMTP reply or a categorised error (cannot connect, TLS failed, authentication failed, sender rejected).

SPF, DKIM and DMARC notes

These are DNS settings for the sender domain, done by the site owner with the relay provider's instructions. General practice (from my own knowledge; no provider has been chosen, so none of this was checked against provider documentation):

  • Send from an address on a domain you control (for example noreply@yourdomain), not from the relay's domain and not from a free-mail address.
  • SPF: publish the provider's include: in the domain's SPF record so the relay is an authorised sender.
  • DKIM: enable DKIM signing at the relay; the provider gives one to three DNS records to add. The signing domain should match (align with) the From domain.
  • DMARC: start with v=DMARC1; p=none and an address for reports, move to quarantine once reports show your own mail passing.
  • The admin settings page shows these three checks as a reminder and the test message lets the owner see where a message lands; the app cannot verify DNS from the settings screen.

Testing

  • Unit tests build messages and assert headers, links and absence of the token after sending.
  • Integration tests run a throwaway SMTP server in the test process (aiosmtpd, dev dependency only) and assert what arrives, including the STARTTLS-required failure case and a permanent-failure case.

Open points for the owner

  • Which relay and sender address will be used (still open as MAIL.1's input). The design works with any standard SMTP relay.

What I could not verify

  • Provider-specific behaviour (limits, port availability, DKIM steps): none chosen.
  • RFC 3834 header semantics and RQ Retry details were recalled, not re-read.
