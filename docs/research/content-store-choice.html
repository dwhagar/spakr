RES.29: Where page content lives, MySQL or git, and how to make it survive damage

Research thread, 2026-10-17. Question from the owner: which is better for content, MySQL or git, with media always in its own directory tree? Added requirement: build from the ground up with checksums and parity so the database can be rebuilt if it is damaged. Measured on Ubuntu 24.04 (4 cores), git 2.43.0, MySQL 8.0.46, par2 from the Ubuntu package. Script: poc/store_bench.py. Builds on RES.4, RES.7, RES.25 and RES.17.

Recommendation

  • Keep git as the source of truth for page content and keep MySQL as a rebuildable index (option A), and harden it. Nothing in the speed numbers forces a change, git is what the owner asked for, and for the new requirement git is the better base: its history is content-addressed, packfiles are immutable and so can carry write-once parity files, and everything MySQL holds about pages can be regenerated from it.
  • Make the git copy complete. Today the type-specific fields live in MySQL and are only "mirrored" in front matter. For a real rebuild the front matter must carry everything about a page that is not derived: fields, tags, settings, visibility, aliases and relations. Then spakr rebuild-index loses nothing. This is the one structural change (GIT.9).
  • Three layers of integrity (planned as INT.3, INT.4, INT.7, INT.10 and INT.13 in the integrity category): (1) detect: git fsck plus a SHA-256 of each page file stored in the index and compared on a schedule; (2) repair in place: par2 parity (10 percent) written for every pack and every backup file; (3) rebuild: restore from the last bundle or a mirror clone, then rebuild the index. Tables that are not derived from git (accounts, keys, audit, settings) get mysqldump plus parity, because they cannot be rebuilt from content.
  • The honest price: a save is about 15 times slower than in MySQL (30 ms against 2 ms) and writers are serialised (about 33 saves a second, measured with 8 competing writers). For a game wiki with a few editors that is far above need. It changes if the numbers in "What would change this recommendation" are reached.

Measurements

5,000 pages of about 2.5 KB (450 words), single host, warm cache. MySQL side: one pg row plus one full-copy rev row per save in one transaction, with the version check done by SELECT ... FOR UPDATE. Git side: the RES.4 design (git binary, working tree, flock).

Reading the table: every user-visible read sits behind the render cache (RES.25), so 0.02 ms against 0.25 ms does not matter. Writes are where MySQL wins by an order of magnitude and where git needs its lock. Storage is where git wins by an order of magnitude, because git stores deltas and MySQL stores a whole copy per revision unless delta code is added. Extrapolating the growth test, 5,000 pages edited 20 times each is about 24 MB in git and about 340 MB in MySQL: both are small on a modern disk, so storage is a backup and portability point more than a capacity point.

The options compared

A = git is the truth, MySQL a rebuildable index (current plan). B = MySQL is the truth, revisions in tables, git only an export. C1 = both written in every request, MySQL read first. C2 = like B but a queue job replays every revision into git (bare repository) for backup and tooling.

What this means

  • Only option A has a layer that can rebuild the database from something other than a backup of itself. In B or C2, the "rebuild" is a restore, and the newest edits since the last dump are the ones at risk. C2 narrows this by exporting to git continuously, which is option A with extra steps and a second writer.
  • Parity belongs on immutable, content-addressed files: packs and bundles. Loose objects (edits since the last repack) are not covered until packed, so the repack job should run daily, not weekly, and write parity for each new pack. The window between edit and parity is covered by the mirror (push after each commit, or a bundle at the next backup).
  • Not everything can be rebuilt. Accounts, roles, API key hashes, sessions, invitations, audit log, settings and the email outbox are not in git. They go in the dump (RES.17) with parity, and a separate small export (JSON lines) of accounts and settings is worth writing beside the git repository so a corrupted database does not need the dump to restart. The audit log is the one table where loss matters and rebuild is impossible.
  • Verify, then repair, then rebuild is the order for a command-line tool: spakr verify (fsck, parity check, compare each page's stored SHA-256 and current_commit with the file), spakr repair (parity repair, then fetch missing objects from the mirror or a bundle), spakr rebuild-index (DB.3).
  • Media is outside this comparison, but the same rule applies: originals are the only irreplaceable files (variants regenerate), each already has a SHA-256 in the media table, and an optional parity file per original is a sensible default for the privately kept originals.

Migration impact on the existing plan and schema

Recommendation A changes no table. It adds, without altering existing columns:

  • page.content_sha256 (CHAR(64)): hash of the page file at current_commit, the cheap drift check. Added to DB.2 (migration 0003).
  • GIT.9 (new): front matter is complete and authoritative (fields, tags, settings, visibility, aliases, relations), so the "fixed export of the non-git tables" shrinks to accounts, keys, audit and settings. Needs RES.13, the front matter schema, and feeds DB.3 and INT.1.
  • Already planned and confirmed by these results: INT.4 (git fsck and page files against the index; also compare the stored hash), INT.7 (parity for the content store: par2 worked on packs, see the table; the choice itself stays with RES.26), INT.9 (journal of MySQL-only data), INT.10 and INT.13 (verify and repair). Suggested wording for them: daily repack so loose objects reach a pack, a mirror push after each commit, and parity written for each new pack.

If the owner chooses B instead, the plan changes more: GIT.1 to GIT.7 become revision-table items (revision table with full copies or deltas, blame code, a git export job for C2), GIT.5 and DB.3 disappear (the index is in the same transaction), and the rebuild requirement is met only by dump plus binary log. That would also remove the owner's git revisioning as a primary store.

What would change this recommendation

  • Sustained edit rates above about 20 saves a second, or more than about 20,000 pages (82 ms a save and growing): then B, or A with the plumbing write path from RES.4.
  • More than one web host: flock and a local repository stop working (B, or a git service in front).
  • A need for atomic multi-page changes with rollback (large imports, rename that rewrites links in many pages): a single git commit under the lock covers it, but if drift between git and MySQL appears in practice during testing (TST), B becomes more attractive.
  • Legal erasure of an author's history that pseudonymous commit identities cannot satisfy.
  • If completing the front matter proves unworkable (for example relations that must be edited from either end), the "git is complete" claim fails and option C2 is the next choice.

What could not be verified

  • Git behaviour above 20,000 files was measured only for the save time; fsck, gc and parity times at that size were not.
  • Parity on loose objects, and parity written automatically after every git gc, were not exercised; the test packed once and damaged the pack.
  • The InnoDB test was one corrupted page in one table; behaviour with innodb_force_recovery and what data can be salvaged was not tried. Whether this MySQL always stops the server on a bad page (rather than failing the single query) was seen on this version only.
  • The MySQL numbers use full-copy revisions; a delta scheme would shrink the storage gap and slow reads and blame. Network latency to a remote database server was not included.
  • SHA-256 object format for git was not tried.
