RES.5: Passwords, sessions, CSRF, tokens and API keys

Research thread B, 2026-10-17. Unblocks AUTH.1 to AUTH.7, AUTH.10, API.4. Recommendation first, evidence after.

Recommendation

  • Passwords: argon2-cffi with its defaults (Argon2id, 64 MiB, 3 passes, 4 lanes), rehash on login when parameters change. Own code around it (about 60 lines); no auth framework.
  • Password policy (NIST SP 800-63B-4 style): at least 15 characters because we are password-only, accept at least 64 (we allow 128), no composition rules, no forced rotation, reject passwords on a blocklist, allow paste and password managers.
  • Sessions: our own server-side sessions (the session table already in the database design). Not Flask's signed-cookie session, not Flask-Login, not Flask-Session. Opaque 256-bit random token in a __Host- cookie, only its SHA-256 stored.
  • CSRF: change the plan from "double-submit token" to a synchronizer token tied to the server session, sent in an X-CSRF-Token header, plus a Sec-Fetch-Site / Origin check as a second layer. API-key requests are exempt.
  • Invitation and reset tokens: random, hashed in the database, single use, delivered in the URL fragment and consumed by a POST (never by opening the link), so mail scanners and server logs cannot use or record them.
  • API keys: spk_ prefix, 256-bit secret, SHA-256 stored (a slow hash is pointless for a random secret), constant-time compare. Keys can use data endpoints only; creating keys, changing passwords or emails and managing sessions require a browser session.
  • Audit log: append-only table written in the same transaction as the action; secrets and tokens never appear in it.

Passwords

  • Hash with PasswordHasher(); store the encoded string (it carries its own parameters) in user.password_hash. On every successful login call check_needs_rehash and rewrite the hash if parameters changed.
  • Normalise the submitted password with Unicode NFKC before hashing; do not trim or truncate. Accept up to 128 characters.
  • Memory cost: each in-flight hash needs 64 MiB. The example vhost runs 2 processes with 8 threads, so 16 simultaneous logins could use about 1 GiB. Guard with a per-process semaphore (for example 4 concurrent hashes) and the login rate limits; an admin setting may lower the memory cost to the OWASP minimum on small hosts.
  • Unknown user: still run one hash against a fixed dummy hash so response time does not reveal which accounts exist.
  • Pepper: not in 1.0. It adds key management and makes rotation hard; revisit after launch.
  • Blocklist: ship a list of common passwords (the licence of the list must be checked when it is chosen; not yet done) and reject matches and passwords containing the username or email local part. An admin switch for the Pwned Passwords range API (k-anonymity: only the first five characters of the SHA-1 are sent) is optional and off by default for privacy; if enabled it goes through the shared outbound helper (FND.4). I am describing that API from memory and did not call it.
  • Multi-factor: not in 1.0. NIST's lower 8-character minimum applies only with MFA, so adding TOTP later would be a policy relaxation, not a requirement. Candidate library pyotp 2.10.0 (MIT).

CSRF

  1. The session row holds a random csrf_token. Login and GET /api/v1/auth/session return it in the JSON body. The JavaScript client keeps it in memory (not local storage, not a cookie) and sends it as X-CSRF-Token on every POST, PUT, PATCH and DELETE.
  2. Reject an unsafe request when the token is missing or wrong (compare with hmac.compare_digest).
  3. Second layer: if Sec-Fetch-Site is present it must be same-origin (or none for user-typed navigations that are safe methods anyway). If it is absent (old browsers), require Origin (or failing that Referer) to match the site's host from site.base_url.
  4. JSON endpoints accept only Content-Type: application/json (uploads accept multipart on their own route). This closes plain HTML form posts as a vector.
  5. No state-changing GET anywhere. The login endpoint is covered by the same origin checks and by rate limits.
  6. Requests authenticated by Authorization: Bearer use no cookie, so they are exempt; a request carrying both is treated as a cookie request.

Plan change: platform.html says "double-submit token issued at login". Because we keep server-side sessions the synchronizer token is simpler and avoids the cookie-injection weakness OWASP describes; platform.html is updated.

Login, invitation and reset flows

  • Login: one generic error for unknown user, wrong password and suspended account; per-IP and per-account throttling (RES.12); audit entry for success and failure (username and IP, never the password).
  • Tokens: secrets.token_urlsafe(32), store only the SHA-256, single use, expiry 7 days (invitation) and 1 hour (reset) as decided, a new token supersedes older ones for the same purpose.
  • Link format: https://site/accept#t=<token>. A URL fragment is never sent to the server, so it stays out of access logs and the Referer header. The page's script reads it, removes it with history.replaceState, and POSTs it. Two problems this avoids: mail scanners that open links (so a GET must never consume a token) and token leakage through server logs. Editing already requires JavaScript, so no non-JS fallback is planned. Pages that handle tokens also send Referrer-Policy: no-referrer.
  • Reset request: always answer "if that address has an account, mail is on its way"; enqueue the work and return immediately so timing is uniform; rate limit per address and per IP.
  • After a reset: do not log the user in; end all their sessions; send a notice to the address; invalidate other outstanding reset tokens.
  • Email and password changes require the current password, send a notice to the old address, and renew the session.
  • Email addresses: syntax check with email-validator 2.3.0 (Unlicense) with deliverability (DNS) checks off on the request path; lower-case before storing.

API keys

ItemDesign
Formatspk_<8-char id>_<43-char secret>. The fixed spk_ prefix makes leaked keys findable by secret scanners. The 8-character id fills api_key.prefix; the secret is token_urlsafe(32).
StorageOnly SHA-256(full key) in key_hash; shown once at creation. A fast hash is correct here because the secret already has 256 bits of entropy.

What a key cannot doCreate, list or revoke keys; change password, email or roles; manage sessions; accept invitations. Those need a browser session, so a stolen key cannot mint more keys or lock the owner out. (New constraint for AUTH.6.)

Audit log

  • Table audit_log as in the database design. Written in the same transaction as the change so an action and its record commit or fail together.
  • Events: login success and failure, logout, session revocation, password change and reset, email change, invitation created and accepted, role and permission changes, user suspend or delete, API key create and revoke, settings changes (names of changed keys only, never secret values), allowlist approvals, upload review and purge, page delete and revert by mods.
  • Fields: actor, action code, target type and id, JSON detail (no secrets), IP, request id, time. Page edits are not duplicated here; git history is their record.
  • Append-only by convention and by privilege: the application's MySQL account gets INSERT and SELECT on audit_log only; retention purges run through the CLI. Whether to enforce that grant is an operations choice for OPS.1; a hash chain for tamper evidence is possible later and not planned for 1.0.
  • Retention of IPs: see the privacy section of platform conventions.
