RES.34: Git or another version control system for page content

Research thread, 2026-10-21. Question from the owner: which versioning system would be best for this purpose, comparing git with other similar version control systems? Measured on Ubuntu 24.04.5 (4 cores) with git 2.43.0, Mercurial 6.7.2, Fossil (Ubuntu package), Subversion 1.14.3. Script: poc/vcs_bench.py. Builds on RES.4 and RES.29. Storing history in MySQL instead was settled in RES.29 and is not revisited here.

Recommendation

  • Keep git. This confirms the current decision (RES.4 and RES.29); nothing in GIT.1 to GIT.9 changes. No other system beats it on the things this site needs, and several lose on something that matters (packaging, licence, Python access, or a missing concurrency story).
  • The closest rival is Subversion, and it is worth saying why it is not chosen. A central server fits a web app well: svnmucc commits a file straight into the repository with no working copy and no lock, 8 writers ran at 120 to 140 saves a second with 0 failures, and a stale edit is rejected by the server as "out of date", which is exactly the edit-conflict rule the site needs. It loses on the things git gives for free: a clone or git bundle is a complete, verifiable, portable backup (RES.17, RES.29), git fsck and immutable packs make parity files simple (RES.29), rename-following history and a built-in three-way merge of text, and a plain folder of Markdown files that anyone can read without the app. Its speed edge is not needed: git's serialised 8 to 30 saves a second is far above what a game wiki needs.
  • Not chosen, and why in one line each: Mercurial (good model, but its Python API is explicitly unstable and GPL, and the command line is slow here), Fossil (superb for a self-contained project site, but one SQLite file and one checkout per writer, no useful library access), Jujutsu (still pre-1.0, no stable API, stores in git anyway), Pijul (pre-1.0, no Ubuntu package), Dolt (replaces MySQL and diffs table cells, not prose).
  • Keep the GitStore wrapper from RES.4. The interface is small (read, write with base check, history, diff, revert, rename), so a different backend could be swapped in later. Jujutsu is the one to watch (see below).

What the site needs from a version control system

Pages are small Markdown files with front matter, edited by a handful of people through a web app. The system is called by Python under Apache mod_wsgi and by a queue worker, on one host, backed up by a script, run by one admin. So the criteria are: safe programmatic use from Python; concurrent writers to different pages without failures; a clean conflict signal for the same page; fast history, diff and blame for one file; per-user attribution; revert; plain-text diff of prose; low disk growth; backups and integrity checks (RES.29); packaged for Ubuntu 24.04 with a licence that fits an MIT project; and operational simplicity.

Measurements

2,000 Markdown files of about 2.5 KB in 50 folders, then edits of single pages and eleven rounds of small edits to 40 pages. Median of 15 runs, in milliseconds, command-line tools called from Python as the app would. Two repeat runs agreed within a few percent. Reading the table. Git is fast at everything except the write, and the write is only slow when writers must wait for each other, which the lock from RES.4 handles. Mercurial's 200 ms per call is Python start-up (the Ubuntu package targets Python 3.12 and needed a wrapper on this machine, which also defaults to 3.13): using it in-process would be quicker but its in-process API is documented as unstable. Fossil's failures are not a bug in Fossil: all writers shared one checkout and Fossil refuses a commit when the checkout changed underneath it, so a web app would need one checkout per writer. Fossil also decides which files changed by modification time, and the benchmark failed until --hash was added, because two edits within one second looked unchanged. Subversion is fastest on writes because the server does the work.

Diffing Markdown

Every system here diffs by line, and a paragraph is one line, so a small edit shows as a whole changed paragraph. This is the same for all of them and so does not decide anything. Git gets --word-diff for free (git diff --word-diff=porcelain), which the history screen (UI.5) can use, and a blame at line level is already fast. Hard-wrapping the text would improve diffs in every system, but it makes the editor worse, so it is not recommended.

Other considerations

  • Per-user attribution. All of them record an author per revision. Git's separate author and committer, and the pseudonymous per-account identity already planned, are enough.
  • GM-only pages. No version control system has page-level access control. The repository must never be exposed raw, whichever system is used (RES.29).
  • Hash algorithm. Git is SHA-1 (hardened against collision attacks) with SHA-256 repositories marked experimental. The app already stores its own SHA-256 per page file (GIT.9, INT.4), so this does not matter.
  • Single point of failure. Fossil keeps everything in one file and Subversion keeps a server-only repository, so a copy of a git repository (full history on every clone, bundle for backup) is a stronger recovery story for a single admin.

Secondary reading: the project's own source code

If the question was about the source control for spakr's own code: it is already on git and GitHub, and versions are numbered by scripts/version.sh (REL.1). No change is suggested.

What could not be verified

  • Jujutsu, Pijul and Dolt were not installed or measured; their rows are from documentation and may have changed.
  • Mercurial's in-process API speed (the unstable API, GPL) was not measured.
  • Scale beyond 2,000 files and roughly a dozen revisions per page, and behaviour on a network filesystem (all of these assume a local disk on one host).
  • Subversion's Python bindings and a long-running svnserve or Apache mod_dav_svn deployment were not tried; only file:// access.

What would change this recommendation

  • Sustained write rates above the lock's capacity (tens of saves a second) with no way to batch: then plumbing-level git (RES.4) first, Subversion-style central commits second.
  • A need for GM-only pages that must also be hidden in history at the storage layer: this would favour a per-group repository, still git.
  • Jujutsu reaching 1.0 with a stable library and a packaged release: it could replace the command-line calls behind GitStore without changing the repository format.
