RES.1: Markdown and MultiMarkdown rendering

Research thread A, 2026-10-17. Unblocks RND.1; feeds RND.2, RND.3, LNK.1, GIT.2. Experiments ran on Ubuntu 24.04.5 (Python 3.12 is the system Python; the experiments used a 3.13 virtualenv, which does not change the results).

Recommendation

  • Use Python-Markdown 3.11.1 (BSD-3-Clause, pure Python, in a pinned virtualenv as decided in RES.15) in-process, with these extensions: tables, footnotes, def_list, abbr, attr_list, toc, sane_lists, fenced_code and wikilinks (with our own build_url for [[Page Name]], LNK.1). Add pymdownx.tilde and pymdownx.caret from pymdown-extensions 12.3 (MIT) so MultiMarkdown-style H~2~O and E=mc^2^ work.
  • This is a MultiMarkdown-compatible dialect, not MultiMarkdown itself. No maintained MultiMarkdown engine is usable on the platform (details below). The dialect is documented for editors (DOC.4) and the differences are listed on this page.
  • Structured page data is YAML front matter (--- block, read with PyYAML 6.0.3 safe_load, MIT), not MultiMarkdown Key: value metadata. Entity fields are lists and nested values, which the MMD block cannot express. The front matter is stripped before rendering.
  • Never run the output without the sanitiser. Python-Markdown passes raw HTML through (measured: <script> and onclick survive). The pipeline is Markdown, then sanitise (RES.3), then swap in trusted math and media markup (RES.2). A working prototype is in docs/research/poc/render_poc.py.
  • No MultiMarkdown file transclusion ({{file}}): it reads files from the server. Excluded on purpose.

MultiMarkdown features and what we do with them

MMD featureIn our dialect
Tables, footnotes, definition lists, abbreviations, header ids, [TOC]Yes (extensions above). Table of contents uses [TOC], not MMD's {{TOC}}.
Subscript and superscript ~ ^Yes, via pymdownx.tilde and caret (tested: H<sub>2</sub>O, E=mc<sup>2</sup>).
Math \\(...\\) and \\[...\\]Yes, hidden from the parser and rendered server-side (RES.2). Both one and two backslashes are accepted.
Metadata block Title: xReplaced by YAML front matter. Python-Markdown's meta extension can read the MMD block, so importing old MMD files is possible later (OPS.6).
Table captions [Caption], column spans ||Not in stock Python-Markdown. Optional: a small custom extension (about 40 lines) if editors ask. Not planned for 1.0.
CriticMarkup, citations, glossary, automatic cross-referencesNo. Page history and diffs (GIT.3) replace CriticMarkup.
File transclusion {{file}}Never (reads server files).
Raw HTMLAllowed in the source but sanitised afterwards; only admin-approved tags and attributes survive.

Measured quirks to handle in RND.1

  • *[HTML]: Hyper Text Markup Language abbreviations also wrapped a literal <abbr> the author had written, giving nested <abbr><abbr>. Harmless; add a test.
  • Python-Markdown prints footnote links with class="footnote-ref" and a back-reference with a title; the sanitiser's attribute rules must keep id, href and the footnote classes (see RES.3).
  • Output uses <table> with inline style="text-align: right" for aligned columns. Our CSP forbids inline styles, so a tree processor must turn alignment into classes (class="align-right"). Same for pandoc. Tested behaviour of the CSP is on the front-end page.
  • Wiki links: the built-in wikilinks extension takes a build_url callable; the prototype maps [[Meridian Fleet]] to /wiki/meridian-fleet. Resolving the slug against the page index and marking missing pages (red links) belongs in LNK.1, after rendering.

What could not be verified

  • Upstream MultiMarkdown 6 status (see table). If the owner wants true MMD 6, a spike is needed with network access to the upstream project.
  • Python-Markdown 3.11.1 on Python 3.12 specifically: it requires Python 3.11 or newer on PyPI, so it is supported, but the test runs used 3.13.

Decision for the owner

Question: the brief says "MultiMarkdown if possible". Accept an MMD-compatible dialect on Python-Markdown (recommended), or require the real MultiMarkdown 6 engine?

Options: (a) dialect on Python-Markdown, recommended: in-process, fast, maintained, safe to extend; most MMD documents render the same; table captions and CriticMarkup differ. (b) Build MultiMarkdown 6 from source: exact MMD output, but we maintain a build on every LTS and still need the sanitiser. Default taken: (a).
