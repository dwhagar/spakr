RES.10: Media toolchain per operation

Research thread A, 2026-10-17. Unblocks MED.4 and MED.5; feeds MED.6. Builds on media processing and RES.9 (type sniffing, thread B). Experiments on Ubuntu 24.04.5: ImageMagick 6.9.12-98, ffmpeg 6.1.1, Pillow 13.0.0 (PyPI).

Recommendation

  • Images: ImageMagick as a policy-limited subprocess. Pillow is faster, but not by enough to matter, produces larger files, and runs inside the worker process (below). Pillow stays for the cheap pre-checks (does it decode, what are the dimensions) as already decided in RES.9.
  • Video and audio: ffmpeg and ffprobe, always (no Python alternative exists that is measurably better). Codecs available in Ubuntu's build: libx264, libx265, libvpx and VP9, libsvtav1, libaom, libopus, libvorbis, libmp3lame, aac, libwebp (checked with ffmpeg -encoders).
  • Ship a tight ImageMagick policy, examples/imagemagick-policy.xml, loaded for the worker only through MAGICK_CONFIGURE_PATH so the system file in /etc is untouched. The Ubuntu default policy blocks only network delegates and @file paths. It still lets text:/etc/hostname read an arbitrary file into an image (verified: it produced an output image). Under our policy the same command fails with "not allowed by the security policy".
  • Always pass an explicit format prefix on input (jpeg:in, png:in) and on output (webp:out.webp) chosen from the already sniffed type, and an argument list with no shell.
  • ffmpeg input is pinned too: -protocol_whitelist file,pipe and, where the type is known, -f mov or -f matroska before -i. Playlist-style inputs (HLS .m3u8, concat) are the classic way to make ffmpeg read other files or fetch URLs; tested below.
  • Limit each job with its own process limits: wall-clock timeout (timeout or subprocess's own), nice/ionice, and memory by cgroup (systemd MemoryMax), not RLIMIT_AS: prlimit --as=300000000 made ffmpeg fail at start-up ("Error while opening decoder") because its threads reserve address space.

Verdict: the ladder is 1.5 times faster in Pillow, a difference of about 0.4 s on a job that runs in a queue worker, nobody waiting. ImageMagick gave smaller files, strips metadata and rotates by EXIF in one command, converts animated GIFs to animated WebP with no extra code (checked under our policy), runs outside the worker's memory and, because it is a process, a crash or hang cannot take the worker down; it also reads limits from the policy file. That is not "measurably better" for Pillow in the sense the plan asks for. Recommended: one ImageMagick process per upload that writes the whole ladder (the mpr: form above), then probe the results with Pillow.

  • Output format: WebP for variants (every current browser reads it); keep GIF/animated as WebP; keep one JPEG poster per video. ImageMagick 6 on Ubuntu can read AVIF and HEIC but not write them (convert -list format shows r--); Pillow 13 can write AVIF. AVIF is a later option, through Pillow, if file sizes matter.
  • Never enlarge (already decided): -resize 1280x> (the > means only shrink) and skip any ladder step not smaller than the original (MED.6).
  • Metadata: -strip removes EXIF including GPS location; -auto-orient first so the picture stays upright. Colour profile handling not tested.

The policy, tested

File: examples/imagemagick-policy.xml. Limits: 256 MiB memory, 64 megapixels area, 16,000 pixels width and height, 1 GiB disk, 30 s time, 2 threads. All coders off except PNG, JPEG, GIF and WebP (in ImageMagick 6 the coder allow-list is the module domain; coder is the ImageMagick 7 name, and the first attempt with it blocked everything).

  • Playlist input is refused. A .m3u8 file pointing at file:///etc/hostname was blocked by ffmpeg's extension check by default and, with -protocol_whitelist file,pipe -f mov forced, the input was rejected as "moov atom not found": the file was never read as media.
  • Timeouts: a 60-second 1080p test source was stopped by timeout 1 with exit code 124; wrap every job in a timeout sized to the file length (for example 4 times the duration, at least 60 s) and a hard maximum.
  • Input limits before transcoding: from ffprobe reject files over the admin's maximum duration, resolution (suggested 3840x2160) and stream count (one video, at most two audio, no data or attachment streams); copy only audio and video streams with -map 0:v:0 -map 0:a:0?.
  • Metadata: -map_metadata -1 strips tags and GPS from the output; keep the original privately as decided.
  • Threads: -threads 2 by default, admin adjustable, so one upload cannot take every core from the website.

Sandboxing

  • Run the worker as an unprivileged user with no network if possible. As a systemd unit (we have no systemd in this container, so these directives were not run here): NoNewPrivileges=yes, ProtectSystem=strict, ProtectHome=yes, PrivateTmp=yes, PrivateNetwork=yes only if Redis is reached over a Unix socket (otherwise IPAddressDeny=any with an allow for localhost), ReadWritePaths= the media directories, MemoryMax=, TasksMax=, CPUQuota= and SystemCallFilter=@system-service. The queue unit examples (FND.6) carry them.
  • bubblewrap and firejail are not installed on this image and not in the plan; systemd's own sandboxing is enough for one host.
  • Per-job directories: each job reads one input file and writes into a fresh temporary directory, then moves the results into the hashed media directory after success. A failed job leaves nothing behind but a log line.

Items this changes

  • MED.4: one ImageMagick process per upload writes the whole ladder (policy file, explicit prefixes, -resize WxH>, -strip, -auto-orient); Pillow only for verification.
  • MED.5: probe first, limits, protocol whitelist, forced input format, timeouts, -map_metadata -1.
  • FND.6 / OPS.7: the policy file is installed to /etc/spakr/imagemagick/policy.xml; the worker unit sets MAGICK_CONFIGURE_PATH.
  • TST: keep the table above as security tests: each hostile input must fail with the policy loaded.

What could not be verified

  • The systemd directives and cgroup limits (no systemd in this container).
  • Pillow 10.2 (the apt version) against 13.0; B's packaging decision uses the PyPI version.
  • Quality comparison beyond file size (no visual or SSIM check), real photographs (the test image was synthetic), colour-profile and HDR handling, and large videos or long encodes under memory limits.
  • ImageMagick 7 behaviour (24.04 ships 6.9.12; the policy domain names differ in 7). Ubuntu 26.04's ImageMagick version was not checked.
