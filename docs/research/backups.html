RES.17: Backups

Research thread B, 2026-10-17. Unblocks OPS.5 and DB.4; informs DOC.3.

Recommendation

One command, spakr backup, writes a dated snapshot directory containing every piece of state, then (optionally) hands it to a standard off-site tool. Restore is spakr restore, and a restore round trip is tested in the daily CI job.

Order and consistency

  1. Take the git write lock briefly (GIT.1) only to read refs for the bundle; releases immediately.
  2. Dump MySQL (consistent snapshot).
  3. rsync media (immutable trees; a file that arrives during the copy is picked up next run).
  4. Write the manifest last. Because git is the source of truth for text and MySQL's page index can be rebuilt (DB.3), small skew between the bundle and the dump is repaired by spakr reindex after a restore.

Encryption and off-site copies

  • Backups contain password hashes, email addresses, GM-only content and the config secrets, so anything leaving the machine is encrypted.
  • Options in the Ubuntu 24.04 archive: age 1.1.1 (encrypt to a public key, private key kept offline), restic 0.16.4 (deduplicated, encrypted repositories over SFTP, S3-compatible storage or rclone; rclone 1.60.1), borgbackup 1.2.8, zstd 1.5.5. Versions are from the archive listing; none were run.
  • Recommended: the script produces the local snapshot and, when backup.offsite_command is set (admin setting, for example a restic command), runs it afterwards. restic is the suggested default in the install guide; the app has no hard dependency on any of them.
  • Optional zero-cost improvement: a configured mirror remote (backup.git_mirror) that the queue pushes to after each content commit, which gives near-zero data loss for page text.

Schedule and retention (defaults, admin-adjustable)

  • Nightly snapshot from a systemd timer (spakr-backup.timer, installed by the install script, with Persistent=true so a missed run happens on next boot).
  • Keep 7 daily, 4 weekly and 6 monthly local snapshots; pruning is part of the command.
  • Retention doubles as the data-retention statement for deleted accounts (see privacy in platform conventions): an erased account can persist in backups until they age out.
  • The database dump alone gives a recovery point of up to 24 hours for accounts and settings; the git mirror shortens it for content.

Restore and testing

  • spakr restore <snapshot> verifies checksums, refuses to overwrite a non-empty database unless forced, restores MySQL, clones the bundle into the content store, rsyncs media, rebuilds the search index (DB.3), then runs requeue-stuck.
  • The daily CI job (07:00 UTC) performs the full cycle on sample content: create, back up, wipe, restore, compare page counts, history and search results. A backup that is never restored is not a backup.
  • DB.4 (database backup and restore script) becomes the MySQL step of this command rather than a separate script.

What I could not verify

  • mysqldump option behaviour on the shipped client (no MySQL server or client in the research environment), rsync snapshot timing at scale, and restic's behaviour with the chosen target.
  • The MySQL 8.0 end-of-support date quoted in some sources was not needed here; Ubuntu 24.04 still receives MySQL 8.0 security builds (8.0.46 in the security pocket, archive listing).
