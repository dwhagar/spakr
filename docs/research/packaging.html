RES.15: Python packaging and dependencies on Ubuntu

Research thread B, 2026-10-17. Unblocks FND.1 and FND.5; informs DOC.3 and OPS.7.

Recommendation

  • System packages from apt; Python libraries from PyPI into a virtualenv. apt provides Python itself, Apache with mod_wsgi, MySQL, Redis, ffmpeg, ImageMagick, git and libmagic. Every Python library (Flask, SQLAlchemy, pydantic, and so on) comes from a pinned virtualenv at /srv/spakr/venv.
  • Python 3.12 (Ubuntu 24.04's system Python). Declare requires-python = ">=3.12". The virtualenv must be created from the system /usr/bin/python3 because apt's mod_wsgi is built for that exact interpreter (RES.16).
  • pyproject.toml (PEP 621) with the setuptools backend and a src/spakr/ package. A lock file with hashes (requirements.lock) generated by pip-compile --generate-hashes (pip-tools 7.6.2, BSD-3) so installs are reproducible and tamper-evident: pip install --require-hashes -r requirements.lock.
  • MySQL driver: PyMySQL (1.2.3, MIT), not mysqlclient. This reverses the earlier default in the media research page; reasons below.
  • SQLAlchemy 2.0.x for 1.0 (lock to 2.0.49, allow <2.2); move to 2.1 after it has matured, since 2.1.0 only appeared on 2026-09-24.

Why PyMySQL over mysqlclient

  • Licence: mysqlclient 2.3.0 declares GPL-2.0-or-later (PyPI metadata); PyMySQL 1.2.3 is MIT. Our code is MIT. We would only be installing mysqlclient, not redistributing it, so using it is arguably fine, but the licence of the combined deployment is a question the owner does not need to carry. PyMySQL removes it.
  • Build: mysqlclient needs a C compiler and MySQL client headers (libmysqlclient-dev, pkg-config); PyMySQL is pure Python, so the install script has fewer apt packages and fewer failure modes.
  • Speed: mysqlclient is faster in raw query throughput, but the workload is read-mostly with rendered-page caching and an index in front of heavy queries. The difference was not benchmarked here; revisit only if profiling points at the driver.
  • Use mysql+pymysql:// in SQLAlchemy; switching drivers later is a one-line URL change.

Layout

pyproject.toml          project metadata, dependency ranges, tool settings (ruff, pytest)
requirements.lock       exact pins with hashes (pip-compile --generate-hashes)
requirements-dev.lock   same for dev tools
src/spakr/              the Python package (app factory, services, models, cli)
src/html/               web root: wsgi.py, cgi-bin/, static/ (as in the example vhost)
tests/                  pytest tests (outside src, so nothing test-related is deployed)
alembic/                migrations, packaged or at the repo root (FND.1 decides)
  • Entry points in pyproject.toml: spakr = spakr.cli:main (FND.9).
  • Version: VERSION holds MAJOR.MINOR; the BUILD number is derived from git (scripts/version.sh). At install or upgrade the script writes the full version into a git-ignored src/spakr/_version.py, so a running app does not need a .git directory. Fallback 0.0.0+unknown if missing.
  • Dependencies are declared as compatible ranges in pyproject.toml and pinned exactly by the lock file; the lock is regenerated deliberately, not by the install script.
  • Note on .gitignore: it ignores *.json globally so config.json is never committed. That also silently ignores JSON test fixtures; add a negation such as !tests/**/*.json when the first fixture is added (FND.7).

Upgrade procedure (input to DOC.3)

  1. Take a backup (RES.17); read the CHANGELOG for the target version.
  2. git fetch and check out the release tag.
  3. /srv/spakr/venv/bin/pip install --require-hashes -r requirements.lock, then pip install --no-deps ..
  4. spakr db upgrade (Alembic upgrade head). MySQL DDL is not transactional (see conventions), so the backup comes first.
  5. Reload: touch src/html/wsgi.py for the mod_wsgi daemon, systemctl restart spakr-worker@* for the queue workers.

26.04 notes

Python 3.14 is a major step. Whether every compiled dependency (pydantic-core, cryptography, argon2-cffi, Pillow, nh3) publishes 3.14 wheels was not checked; 26.04 support stays best effort, with a CI job added when the project has code to run (OPS.7). The same venv approach works unchanged.

What I could not verify

  • Wheel availability for Python 3.14 (26.04) and performance difference between the MySQL drivers.
  • That pip-compile --generate-hashes behaves as expected with every dependency (done when the lock is first generated, FND.1).
