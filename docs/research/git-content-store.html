RES.4: Git access from Python

Research thread A, 2026-10-17. Unblocks GIT.1; feeds GIT.2 to GIT.7 and DB.3. Experiments on Ubuntu 24.04.5 with git 2.43.0 against a repository of 5,001 Markdown files and 178 commits, using dulwich 1.2.17, GitPython 3.2.1 and pygit2 1.20.1 from PyPI.

Recommendation

  • Call the git binary through subprocess (argument lists, never a shell), behind one small GitStore class so the choice can change. Ubuntu 24.04 ships git 2.43.0; no Python git library is needed. This was the fastest write path, the only one with nothing to pin or audit, and it keeps every git behaviour (renames, log --follow, gc) exactly as users of the repository know it.
  • One non-bare repository owned by the app user. Page files live at type/shard/slug.md (the test used 50 shards per type, 5,000 pages) so no directory holds thousands of entries. The newest content is read straight from the working-tree file (5 microseconds when cached by the OS), history and old revisions come from git.
  • All writes go through one exclusive lock: fcntl.flock on a lock file beside the repository. Measured: with no lock, 7 of 8 simultaneous commits failed with fatal: Unable to create '.../index.lock'; with the lock, 0 of 8 failed. The lock covers: check the base commit, write the file, git add, git commit, update the MySQL index row. It works across the web processes and the queue worker on one host (not over NFS).
  • Edit conflict detection (GIT.7) compares the commit that last touched the file (git log -1 --format=%H -- path, 3 to 18 ms) with the base commit the editor started from, inside the lock. Different pages never conflict; the same page conflicts only if it changed since the editor opened it.
  • Safe invocation: always git -C repo, a -- before every path, slugs validated by GIT.6 (no .., no leading dash, no control characters), and -c core.hooksPath=/dev/null -c commit.gpgsign=false -c core.quotepath=false with GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_NOSYSTEM=1 so no global setting changes behaviour (a stray signing configuration made dulwich's commit fail in testing). Author and committer are set per commit with --author and environment variables using the pseudonymous per-account identity from platform conventions.
  • Crash recovery: the store runs git status --porcelain under the lock at start-up and before each write; a dirty tree left by a crashed write is reset with git checkout -- . and git clean after being logged. spakr fsck (FND.9 candidate) runs git fsck and compares the MySQL index with the tree (DB.3).
  • Housekeeping: a weekly queue job runs git gc --auto (the test repository had 5,407 loose objects). Backups use git bundle as decided in RES.17.

A single edit costs 26 ms of git work; the other pieces of a save (Markdown to text for the search document, the MySQL write) are of the same order, so the git choice is not the limit. Reads of the current page come from the cache or the working tree, not from git.

The libraries

OptionLicenceAssessment
git binary (chosen)GPL-2.0, separate process, so no linking questionFast writes and history, exact git semantics, nothing to pin. Cost: process start per call (about 3 ms) and parsing text output; mitigated by one git cat-file --batch reader process only if profiling shows a need.
pygit2GPL-2.0 with the libgit2 linking exception (as declared on PyPI)Fastest reads by two orders of magnitude and a good commit time, but it is a C extension, a crash inside libgit2 takes the web process down, and path history needs a manual commit walk (no rename following). The upgrade path if profiling ever shows git reads matter; keep the GitStore interface so it can be swapped in.
dulwichApache-2.0 or GPL-2.0-or-laterPure Python, easy to deploy, but 7 to 8 times slower to commit here (it re-checks the index of 5,000 files) and 8 times slower for path history.
GitPythonBSD-3-ClauseMostly a wrapper around the git binary with its own overhead; slowest commit; leaked processes and file handles in long-running programs are a commonly reported problem (from general experience, not reproduced here). No advantage over calling git directly.

Design choices behind the numbers

  • Working tree or bare plus plumbing? The plumbing route (hash-object, temporary index, write-tree, commit-tree, update-ref with the expected old value) costs 41 ms against 26 ms and gives an atomic compare-and-swap and no dirty tree. The simpler porcelain route is chosen because the lock already serialises writers and the recovery step handles the crash case. If a second writer ever appears (for example an import tool), the plumbing route is the fix.
  • Rename and move (GIT.6): git mv in the same locked commit, and keep old slugs as aliases in the database (they are also search aliases, RES.7). git log --follow shows history across the rename (not benchmarked).
  • Revert (GIT.4): git revert --no-edit would revert the whole commit; page reverts should check out the old blob into the working tree and make a normal commit with reverts_commit recorded, as the database design already says.
  • Binary files stay out of git: media is not in the content repository (originals and variants are on disk and in media tables), so the repository stays small text.
  • Locking in Python: open the lock file once per operation, flock(LOCK_EX) with a timeout (non-blocking attempts in a loop; give up after about 10 s with a retryable error), close in finally. In testing, forgetting to close the descriptor in a thread deadlocked every later writer: use a context manager.

What could not be verified

  • Scaling beyond 5,000 files and 178 commits: repository behaviour with 50,000 files was not measured (the content set for a game database should stay in the thousands; the numbers will grow with the file count, mostly for git add on the index).
  • Behaviour on a network filesystem: flock is local-host only. The deployment is single host (RES.16).
  • pygit2's rename-following history and its memory use under mod_wsgi.
