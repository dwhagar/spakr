RES.14: OpenAPI generation and API conventions

Research thread B, 2026-10-17. Unblocks API.1 to API.3, DOC.5. Also settles error format, versioning and conflict handling that the other API items depend on.

Recommendation

  • Pydantic v2 models + SpecTree (spectree 3.0.0). Request and response schemas are pydantic models; SpecTree validates requests, and generates an OpenAPI 3.1 description from the same models. Routes stay ordinary Flask functions.
  • If SpecTree disappoints in the first real routes, the fallback is flask-openapi3 (same idea), then a small in-house registry; the pydantic models are the part that stays.
  • Errors: application/problem+json (RFC 9457). Pagination: opaque cursors. Edit conflicts: ETag and If-Match carrying the git commit.
  • Serve the description at /api/v1/openapi.json; publish human documentation as a static page (DOC.5), not a runtime UI that loads scripts from a CDN.

Why pydantic fits this project

  • Entity pages have per-type structured fields (RES.13, ENT.1). Pydantic's create_model can build a model per entity type at start-up, and the same model gives validation, the OpenAPI schema and the JSON Schema the UI needs for its forms (ENT.13). This design is intended but I did not test it in the spike.
  • Pydantic 2.14.1 (MIT) works under Apache's mod_wsgi on Ubuntu 24.04; see RES.16 (tested). Ubuntu 24.04's apt ships pydantic 1.10, so the venv is required.

Cautions found

  • SpecTree answers validation failures with HTTP 422 and its own body. We want the same problem+json body as every other error (below). SpecTree's validation-error hook must be set to our formatter; the spike did not exercise that hook.
  • SpecTree's built-in documentation pages load Swagger UI, Redoc and Scalar from unpkg and jsDelivr (confirmed by reading its source). Our Content-Security-Policy forbids third-party scripts. Disable those routes in production; generate documentation statically (DOC.5) from openapi.json, or vendor the assets from our origin.
  • Version risk: three of the candidates are single-purpose libraries with a small maintainer base. Because routes stay plain Flask and models are plain pydantic, replacing SpecTree later changes only the decorator.

API conventions (for API.1 and API.2)

TopicConvention
VersioningMajor version in the path (/api/v1). Adding fields, endpoints or optional parameters is not a breaking change and stays in v1; removing or changing meaning requires /api/v2 running beside v1 for a stated period. Every response carries X-API-Version: 1. Deprecations use Deprecation and Sunset headers (RFC 9745 and RFC 8594; recalled, not re-read).
ErrorsRFC 9457 problem details, Content-Type: application/problem+json, fields type, title, status, detail, instance, plus request_id and, for validation, an errors list of {field, message, code}. Never include stack traces, SQL or paths. Status codes: 400 malformed, 401 not signed in, 403 forbidden, 404 not found (also for pages a user may not see, so existence does not leak), 409 conflict, 412 precondition failed, 422 validation, 429 rate limited.
PaginationList endpoints take limit (default 20, maximum 100) and an opaque cursor; responses return items and next_cursor (null at the end). Cursors are signed with a key derived from secrets.secret_key so they cannot be forged. Search results use the same shape and may add total when cheap.
Filtering and sortingSimple query parameters (type, setting, tag, q, sort with a documented whitelist). Unknown parameters are an error, not ignored, so typos do not silently return everything.
Edit conflicts (GIT.7)GET a page returns ETag: "<commit sha>"; PUT requires If-Match with the base commit. A mismatch returns 412 with the current revision so the UI can offer a merge or diff.
Content typesRequests and responses are JSON (application/json), except uploads (multipart) and media downloads. Anything else gets 415.
CachingAuthenticated responses Cache-Control: no-store and Vary: Cookie, Authorization (already in the plan); public GETs use the page ETag so a CDN or browser can revalidate.
IdempotencyPUT and DELETE are idempotent; creation endpoints accept an optional Idempotency-Key header from API clients (stored for 24 hours) so retried scripts do not duplicate pages. Optional; can be dropped if it complicates 1.0.
Contract testsCI validates the generated description with openapi-spec-validator and fuzzes the running API against it with schemathesis 4.31.1 (MIT) in the daily job; tests also assert that every route appears in the description.

What I could not verify

  • SpecTree's custom validation-error handler and its behaviour with dynamically created models (spike covered static models only).
  • RFC 9457, 9745 and 8594 details were recalled; the RFC site was unreachable. Re-read before API.2 is merged.
  • Single-maintainer risk is an inference from small project size, not a measured fact.
