RES.11: Front-end approach, CSP, dark mode and responsive base

Research thread A, 2026-10-17. Unblocks UI.1; feeds RND.4, UI.11 to UI.14. Research C owns the detailed questions RES.21 (CSS and design system), RES.22 (is Node justified), RES.23 (device range) and RES.24 (components); this page gives the evidence that holds under any of their answers: what the strict Content-Security-Policy allows, and the baseline for themes and layout. Browser checks ran in Chromium 141 through Playwright.

Recommendation

  • Reading is plain server-rendered HTML and CSS; JavaScript is an enhancement. Public pages (UI.2) need no script. JavaScript is for the editor, search-as-you-type, forms and admin screens, as native ES modules served from our origin with a plain <script type="module" src="...">.
  • Start with no framework and no build step for 0.1 (UI.1): native modules, fetch() to /api/v1, and, where a component helps, standard custom elements (they work under the strict CSP, tested). Revisit a small library or bundler only when RES.22 and RES.24 decide; the CSP rules below constrain which ones qualify.
  • The strict policy is the target from the first commit (RND.4): default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self'; media-src 'self'; font-src 'self'; connect-src 'self'; manifest-src 'self'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'; object-src 'none', with X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin and a restrictive Permissions-Policy. No nonces, no 'unsafe-inline', no 'unsafe-eval'. TLS and HSTS belong to Apache and API.6, assumed in place.
  • Asset versioning without a bundler: serve scripts and styles with Cache-Control: no-cache plus an ETag; the browser revalidates and gets a tiny 304. A page links app.css?v=<hash> using a version string computed at start-up (hash of the file contents). For immutable caching later, a build step copies files to content-hashed names and rewrites relative import specifiers (about 40 lines of Python); do that only if RES.22 says Node or a build step is accepted anyway.
  • Editor: a plain <textarea> with the preview endpoint (RND.6) for 0.8. CodeMirror 6 (MIT; codemirror 6.0.2, @codemirror/view 6.43.14) gives syntax highlighting and accessibility work already done, but it must be bundled, so it is a RES.22-dependent upgrade, not a 1.0 requirement.
  • Themes: CSS custom properties for every colour, defaults from prefers-color-scheme, user override as a data-theme attribute on <html> written by the server from the stored preference (UI.12), so there is no inline script and no flash of the wrong theme. Same pattern as the plan pages' style.css.
  • Responsive base: mobile-first single column, fluid type, tables in a scroll wrapper (the renderer adds the wrapper, trusted markup), no horizontal page scroll at 360 px. Device ranges (foldables, TV) are RES.23.

What the strict CSP does and does not break (Chromium 141)

TechniqueResult under the policyConsequence
Inline <script>Refused (console error, did not run)No inline scripts or event-handler attributes. Pass data with data-* attributes or a JSON <script type="application/json"> (data blocks are not executed).
style="..." attributes in markup, including innerHTMLRefusedAuthor HTML has style stripped (RES.3). The renderer emits classes, not styles. Libraries that emit style attributes (KaTeX's HTML output: 57 of them for one formula) are out.
element.style.color = ..., style.cssText, constructed stylesheets (adoptedStyleSheets)WorkScripted styling through the CSSOM is fine. setAttribute('style', ...) is blocked.
eval() and new Function()Blocked (EvalError)Libraries that compile templates or expressions at run time need a CSP-safe build or are excluded. Alpine's default build is documented to need unsafe-eval and ships a separate CSP build; htmx has an option to disable evaluation (both from their documentation as I know it, not tested here).
External stylesheet and ES modules (static and dynamic import()), fetch() to our originWorkThe planned structure.
Custom elements (web components)WorkA no-library component model is available.
MathML from Temml with style attributes removedRenders; display math stays a block through the shipped CSS classSee RES.2.
<script type="application/ld+json">Readable, no violationSee RES.8.
import maps (<script type="importmap">)Inline, so it needs a nonce or hash (not tested)Avoid; use relative imports.

Dark mode and responsive checks

  • A test page with color-scheme: light dark and light-dark() colour tokens, loaded with the browser in each scheme, resolved to the dark values in the dark run (background rgb(20, 22, 26), text rgb(230, 232, 235)) and the light values in the light run (white background, rgb(27, 31, 36) text), and the maths inherited the text colour. A screenshot of the dark run shows readable text and formulas.
  • At a 390 px wide viewport the test page had no horizontal scroll (scrollWidth not larger than the viewport) in both schemes.
  • light-dark() works in this Chromium; it is a recent CSS function (browsers added it during 2024, from memory; no compatibility table could be fetched). For the production tokens use the plain @media (prefers-color-scheme: dark) variable override (as the plan pages do), which works in every browser, and :root[data-theme=dark] / [data-theme=light] overrides after it; light-dark() is an optional nicety. Always set color-scheme so form controls, scrollbars and the canvas colour follow.
  • Container queries parsed without error in the test stylesheet; their layout effect was not tested (RES.21 and RES.23 decide how much to rely on them).
