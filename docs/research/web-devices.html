RES.23: small phone to big-screen TV

Research thread C, 2026-10-17. Breakpoints, fluid type, foldables, 10-foot layout, remote-control focus, safe areas and the test matrix. Part of the web layer research; the prototype in web-prototype implements and tests everything below.

Recommendation

  • One layout that responds to the space it has, not to a device class. Mobile first; the only layout breakpoint is 62rem (about 990 px: sidebar and editor go side by side). Everything else is fluid: clamp() type and spacing, minmax() grids, max-inline-size in ch for readable lines. A phone, a folded or unfolded foldable, a tablet in either orientation and a window of any width all get the same rules.
  • TV is a mode, not a guess. A "TV" toggle (stored with the account or a cookie and rendered by the server as data-ui="tv") scales the whole UI through the root font size (125 percent, 175 percent from 2400 px wide), adds overscan-safe margins (5 percent), larger targets, a thick focus ring and turns on arrow-key focus movement. It is also suggested automatically when the device has no pointer at all and the window is at least 1280 px wide (@media (any-pointer: none)); that heuristic is not verified on real TVs.
  • Browsers are an input, not a surprise: TV browsers are years behind desktop ones, so the CSS is written so that a missing feature costs polish, never legibility (see policy below).
  • Print, reduced motion, high contrast and forced colours are handled in the same stylesheet.

Foldables

  • A phone-style foldable (Galaxy Z Fold type) is simply two viewport sizes: a narrow cover screen and a tablet-like inner screen; the page is resized on fold and unfold. Fluid layout handles it; tested at 280x653 and 884x1104 CSS px (representative sizes from memory, not measured from a device). No overflow, targets 44 px or more, axe clean.
  • Dual-screen spanning devices (a hinge between two panels) have a separate set of web features: the horizontal-viewport-segments and vertical-viewport-segments media features and env(viewport-segment-*) constants. I could not verify their current browser support (MDN unreachable). Treat them as an optional later enhancement for the editor (write pane on one panel, preview on the other); the prototype does not depend on them and uses env(safe-area-inset-*) padding with viewport-fit=cover so content avoids notches and rounded corners.
  • Orientation is never locked (WCAG 1.3.4).

What this means for the CSS and HTML

  • Support policy: full support for Chromium 94 and later (covers 2023 TVs and newer); readable but plainer on Chromium 85 to 87 (2022 TVs: logical positioning properties such as inset-block-start arrived in Chromium 87, from memory, so a sticky header or skip link may misplace); best effort on Chromium 76. This policy is a proposal for the owner to confirm. The prototype could not be tested on those engines here (Chromium 141 only).
  • MathML is a real risk. Native MathML rendering came back to Chromium in version 109 (from memory). TVs on Chromium 108 or older would show the content of a <math> element as plain, unformatted text. RES.2 (server-side LaTeX) should therefore emit MathML with the TeX source in an alttext attribute and be tested on an old engine; a server-side SVG or image fallback for TV user agents is the alternative. Flagged for the RES.2 thread; I did not test an old engine.
  • Avoided on purpose: @layer (whole block dropped if unknown), CSS nesting, light-dark(), :has() for anything essential, dvh without a vh fallback (used with fallback).
  • Many TVs report 1920x1080 CSS pixels even on 4K panels (device pixel ratio 2), from memory; some report the raw 3840x2160. Both were tested here, 1920x1080 and 3840x2160 at ratio 1: no overflow, readable body text (24.6 px and 35 px).
  • Overscan and safe areas: 5 percent side padding in TV mode (max(5vw, env(safe-area-inset-*))). Vertical overscan margin is not added; sticky bars are disabled in TV mode so nothing sits against the screen edge.

Remote-control navigation and focus

  • Browsers do not ship spatial navigation. The CSS Spatial Navigation draft (last W3C working draft November 2019, search results) is not provided by default; the focusgroup proposal could not be checked (search found nothing). So the prototype has its own 25-line module (nav.js): in TV mode the arrow keys move focus to the nearest focusable element in that direction, preferring elements in line with the current one. When nothing is in that direction, the key falls through to normal scrolling, so long prose scrolls with the remote.
  • Test result: from the first nav link, ArrowRight focuses the next link (script-checked). Not tested with a real remote, whose Back, colour and media keys use platform-specific key codes (Tizen's Back key is a non-standard code, from memory). A thin per-platform key map belongs in a later UI item.
  • Focus must be visible from ten feet: 0.3 rem outline plus a dark halo in TV mode, in both themes (the dark theme uses a yellow focus colour). :focus-visible is used everywhere, so mouse users are not shown rings.
  • No hover-only controls; every action is a real button or link, reachable by Tab and arrows; no drag-only interactions (also WCAG 2.5.7).
  • Text entry on a TV is painful, so TV mode is for reading, browsing and searching; editing and uploading on a TV are out of scope. The search field relies on the platform's on-screen keyboard.
  • Video and audio use the native controls and platform fullscreen: they are already remote-friendly. Third-party players would need their own remote support checked.
