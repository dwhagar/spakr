RES.7: Search approach

Research thread A, 2026-10-17. Unblocks SEARCH.3 and SEARCH.8; changes SEARCH.2 and SEARCH.8 (see below); feeds SEARCH.4 to SEARCH.7. Trials ran on a real MySQL 8.0.46 server (the Ubuntu 24.04 package) with the page_search table from the database design.

Recommendation

  • Use InnoDB FULLTEXT with the default parser, no external search engine for 1.0. It handles the three search modes in the design (name, all-field, field filters) at 2 ms (5,000 pages) to 36 ms median (50,000 pages) per query, adds no service to run, and the index lives in the same database and transactions as the rest.
  • Do not use the ngram parser. It fixed short tokens but was 10 to 25 times slower, and noisy for English (a search for Varn also returned Urnevel Marne and similar names through shared two-letter pieces).
  • Two server settings matter, and they are not application settings (this changes SEARCH.8): innodb_ft_min_token_size=2 and innodb_ft_enable_stopword=OFF. They are read when MySQL starts, live in mysqld.cnf, and changing them means rebuilding the index. SEARCH.8 as written ("set by the admin" in the web interface) cannot work. Instead: install guide (DOC.3) tells the admin to set them, the application checks @@innodb_ft_min_token_size and @@innodb_ft_enable_stopword at start-up and warns on the admin screen when they are wrong, and the search document builder works well enough with the defaults (below) so nothing breaks if they are not set.
  • Rank with a title boost by combining the two indexes in the query: 3 * MATCH(title, aliases_text) + MATCH(all columns). Plain all-column ranking put a page full of the word first; the combined score fixed it (below).
  • Snippets and highlighting are the application's job; MySQL does not produce them. Cut them from body in Python for the top 20 results only.
  • Keep the index behind one SearchIndex interface (SEARCH.2, SEARCH.3) so an external engine can replace it later without touching the API.

What the trials taught us

  • Short tokens are the real RPG problem. Game text is full of two-letter terms: HP, AC, XP, AI, GM, Mi-Go, Ka-Tet. With MySQL's defaults none of them can be found. Setting the minimum to 2 fixes it at the cost of a larger index (not measured: InnoDB keeps FULLTEXT data in auxiliary tables that information_schema reports as zero, so the size effect is unknown). This is why the setting should be in the install guide, not left optional.
  • Dice and stat notation is one token. 8d6 is found; d6 is not found inside it. SEARCH.2 (document builder) should add the split forms to the field text: for each token like 8d6 also write d6; for hyphenated names also write the joined form (migo); for names with apostrophes also the joined form (dunkar). This is cheap and works under the default settings too.
  • Stop-words only hurt titles. With them on, The Void still worked, because the other word carries it. A page named just "It" or "Them" (horror fiction has these) would be unfindable, which is another reason to turn the list off.
  • No 50 percent rule. InnoDB natural-language mode returns results for words that occur in most pages (unlike MyISAM), so an all-pages word simply ranks low; no surprises for editors searching common terms.
  • Updates are cheap. A single-row update with FULLTEXT cost 2.8 ms (50,000 rows); loading 50,000 pages took 26 s. The index becomes visible when the transaction commits, which is the behaviour we want (write git first, then MySQL, as in RES.4).
  • Size: 50,000 generated pages (about 350 words each) were 174 MB of table data. A real game database will be far smaller.

Alternatives

OptionVerdict
InnoDB FULLTEXT, default parserChosen. Right size for thousands of pages; one less service; the same database holds visibility, tags and settings, so one query applies all filters (SEARCH.4 to SEARCH.6).

Typo tolerance and faceting are good, but each is another service to install, secure, back up and keep in step with git. Not justified at this size. Licences and current versions not verified (project sites were not reachable from this session).

Effect on the plan

  • SEARCH.8 becomes "install requirement and start-up check for the two server variables" (not an admin web setting); the ngram choice stays an install-time choice. Text updated in TODO.md.
  • SEARCH.2 additionally writes the split and joined token forms described above.
  • SEARCH.3 uses the title-boosted combined query and builds snippets in Python; no 50 percent rule to work around.
  • DOC.3 and FND.9: the install guide lists innodb_ft_min_token_size=2 and innodb_ft_enable_stopword=OFF; spakr reindex rebuilds the index after a change (OPTIMIZE TABLE or a rebuild).

What could not be verified

  • Relevance on real wiki text: the corpus words were random; the hand-written pages tested ranking rules, not language. Re-run the trial when TST.3 (sample content) exists.
  • MariaDB behaviour, SQLite FTS5 and the external engines were not run.
  • Index size effect of min_token_size=2 on real text.
