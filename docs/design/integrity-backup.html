Integrity, parity and backup design

Design thread, 2026-10-22. Settles RES.26 (parity), RES.27 (source of truth), RES.28 (checksums) and RES.30 (backup). Unblocks INT.1, INT.2, INT.3, INT.7, INT.9, BAK.1 and BAK.8. Builds on RES.29 (git is the source of truth for page content), RES.17 and RES.31 (redacted config in backups). Measurements: poc/integrity_bench.py, Ubuntu 24.04, 4 cores, par2cmdline 0.8.1, Python 3.12.

Summary

  1. Every stored thing has one class: source of truth (S), rebuildable (R) or disposable (D). Only S needs backup and a journal; R is rebuilt by a command; D is ignored. The full table is in section 1.
  2. Hash: SHA-256 everywhere. On this machine it ran at 1,263 MB/s, faster than BLAKE2b (557 MB/s) and SHA3 (347 MB/s), it is the algorithm the database design and media directories already use, and it is checkable with stock sha256sum.
  3. Parity: par2 on immutable files only (backup archives, git packs and bundles, media originals). Not zfec, not reedsolo, not filesystem-specific. 10% redundancy repaired three scattered damaged spots in a 100 MB file in 1.7 s.
  4. MySQL-only data is journaled to hash-chained, fsynced files before commit, so accounts, settings and the audit log can be rebuilt without the last dump.
  5. Backup = small core archive nightly + a content-addressed media pool that only ever receives new files. Media is incompressible, so it is never run through bzip2 or gzip. This departs from a literal "tar.bz2 of everything" and is Question Q1 below.
  6. Nine open questions only the owner can settle are in section 7, each with options and a recommendation.

1. Classification of everything stored (RES.27)

Classes: S source of truth (losing it loses information; must be backed up, checksummed, and for MySQL-only data journaled), R rebuildable from S by a named command, D disposable. Table names are from the database design.

1.1 Two structural consequences

  • Media sidecar. The original bytes cannot say who uploaded them or whether a moderator approved them. A small meta.json written atomically next to the original (and rewritten on state changes) makes media rebuildable from /data/media alone. The MED items need to write it; the media state machine stays the same.
  • Stable user reference in git. Rebuilding page_revision.author_id from commit authors needs commits to carry an opaque, permanent user identifier (not an email), and the user table to store it (Q8).

2. Checksum design (RES.28)

2.1 Algorithm

Algorithm (100 MB, hashlib)TimeRate
crc32 (not a hash; for reference)31 ms3,239 MB/s
SHA-25679 ms1,263 MB/s
BLAKE2b180 ms557 MB/s
SHA-512177 ms566 MB/s
SHA3-256288 ms347 MB/s

SHA-256 wins here because the CPU has SHA instructions and OpenSSL uses them; on a CPU without them BLAKE2b would be faster, but that is not the deciding point. Decision: SHA-256 for every checksum, hex lower-case, 64 characters. Reasons: media.sha256 and api_key.key_hash already use it; GNU sha256sum verifies it with no spakr code (useful in a disaster); one algorithm means one helper (INT.3). The algorithm name is stored in each manifest header so a later change is a version bump, not a flag day. Rejected: BLAKE2b (extra length and name variations for no gain on supported hardware), SHA-1/MD5 (not for new integrity records; git's own SHA-1 is untouched and is covered by git fsck plus the SHA-256 recorded in the index), CRC (detects accidents but is trivially forgeable).

2.2 Manifest format and location

The one place a manifest is really needed is where there is no content-addressing already: backups, parity sets and journal segments. Media originals self-verify by directory name; variant hashes live in meta.json; git is content-addressed and gets one SHA-256 per page in the index.

  • Disk format: SHA256SUMS-compatible text, one hash relative/path per line, preceded by # comment lines (header: spakr-manifest 1, algorithm, creation time, software and schema version). Tested here: GNU sha256sum -c accepts the comments, and reports OK or FAILED per file with exit code 0 or 1.
  • Last line is # manifest-sha256 <hash of every preceding line>, so a truncated or edited manifest is detected before it is trusted.
  • Backups additionally carry manifest.json (BAK.4) with the richer record: component list, sizes, git tip, journal sequence, per-table digests. The SHA256SUMS beside it lists the archive, parity and manifest.json itself.
  • Location: next to what it describes (/data/backups/<name>/, /data/parity/<store>/, /data/journal/<day>/). Written to a temporary name, fsynced, renamed (INT.3).
  • Rejected: one global manifest of the whole of /data (a single point of failure, a lock hot-spot, and it must be rewritten on every upload); manifest only in MySQL (the database is what we are protecting).

2.3 Database checksums

  • Migration records. schema_migration stores the SHA-256 of each migration file as applied. At start-up and in spakr verify, a mismatch refuses to run (INT.2). The integer DB schema version still counts up on every change.
  • Row hash on S-class tables. A row_hash CHAR(64) column holds SHA-256 over a canonical encoding of the row's other columns in a fixed order, each value prefixed with its length and NULL encoded distinctly, so ("ab","c") and ("a","bc") cannot collide. Computed by the data-access layer in Python in the same transaction as the write. It is unkeyed: it detects corruption and sloppy manual edits, not a determined attacker with write access (they can recompute it). Rejected: a MySQL stored generated column using SHA2(CONCAT_WS(...)) (it would auto-maintain itself, but NULL, collation and number-format rules differ from the Python verifier and make cross-checking fragile); triggers (hidden logic, harder to test); relying on CHECKSUM TABLE (an internal value that changes with row format and server version; usable only as a same-server before/after comparison).
  • Table digest. SHA-256 over the row hashes ordered by primary key, recorded per S-class table in the backup manifest. After a restore it proves the table came back whole, without comparing row by row.
  • Audit hash chain. audit_log.prev_hash and audit_log.hash where hash = SHA-256(prev_hash || canonical row). Inserts are serialised by one chain-head row locked with SELECT ... FOR UPDATE; audit volume is low (moderator and admin actions), so this costs nothing noticeable. A chain implemented in Python ran at 4.3 microseconds per row (100,000 rows in 432 ms), so verifying a million rows is a few seconds of CPU plus the read. A chain only proves tampering if its head is stored somewhere an attacker with database access cannot rewrite, so the head is also written into the journal, every backup manifest, and optionally signed (Q6).
  • Git. page.content_sha256 (GIT.9) is compared with the working-tree file by the scheduled check; git's own object hashes are verified by git fsck (0.20 s for 5,000 pages in the RES.29 measurements). The backup manifest records the git tip SHA, and git's commit chain is itself a hash chain over page history.

3. Parity (RES.26)

3.1 Options measured

OptionResultVerdict
par2cmdline (Ubuntu package par2 0.8.1)100 MB file: create 1.9 s / 2.8 s / 4.8 s at 5% / 10% / 20%; parity 5.6 / 10.9 / 21.4 MB; verify 0.76 s. Three damaged 2 KB spots: repaired, byte-identical, 1.7 s at every level. 30 MB wiped (more than the redundancy): repair refused with exit code 2, file left unrepaired, no false success.Chosen. Mature, standard file format, self-verifying, verify and repair in one tool, in the Ubuntu archive.
zfec (Python)Encoding 100 MB at 10% took 0.07 s, far faster than par2.Rejected: a library, not a tool. We would have to write the file format, block checksums, damage localisation and repair command ourselves, which is the part par2 already does and the part that goes wrong.
reedsolo (pure Python)About 2.6 s per MB, so about 260 s for 100 MB.Rejected: 90 times slower than par2 for a video.
Filesystem: ZFS or btrfs scrub with redundancy, dm-integrity, RAIDNot measured; needs root, a particular disk layout, and a second disk for self-healing.Not required. Ubuntu installs on ext4 and the app cannot assume it. Documented in the admin guide as an optional extra layer that complements, not replaces, par2.

Caveats from the run: par2 on 5,000 small files in one command exited with an error (code 3) in my invocation and I did not pursue it; parity for many tiny files is the wrong shape anyway. Parity for a 1 KB git pack cost about 36 KB (a fixed overhead per parity set), so tiny files should be grouped. The 30 MB case is a design limit, not a bug: parity covers bit rot and bad sectors, not a lost disk, which is what the backups are for.

3.2 What gets parity, when, where

Git packs and media originals are immutable once written, so parity is created once and never refreshed, which is what makes it cheap. The gap is loose git objects and the newest pack: a window of at most one day, covered by the nightly bundle and the git mirror option from RES.17. Not covered by parity and said so honestly: files being written right now, the parity files themselves (a damaged parity set is detected by its own checksums and regenerated from healthy data), and anything on a failed disk.

Defaults: 10% redundancy for archives, packs and the journal, a configurable value for media (Q4). par2 is invoked with an argument list (never through a shell) and paths checked to be under /data. Parity is sensitive as the data it protects, so it is stored 0600 in 0700 directories. For encrypted off-host copies the order is encrypt first, then par2 the ciphertext, so parity never exists for plaintext outside the machine.

3.3 Recovery procedure

  1. spakr verify finds damage and names the files.
  2. spakr repair (INT.13) runs par2 repair on the affected file, re-hashes it against the manifest or its hash directory name, and writes an audit entry.
  3. If par2 reports exit code 2 (too much damage), the file is quarantined and restored from the newest backup that contains it; for git, from the bundle, then git fsck and reindex.
  4. Derived data is then rebuilt (R-class), and a full verify confirms.

4. The MySQL journal (shapes INT.9)

Why it exists: without it the recovery point for accounts, keys, settings and audit is the last dump, up to 24 hours. With it the database can be rebuilt to the last committed change without MySQL's help.

  • Format: JSON Lines in /data/journal/YYYY/MM/DD.jsonl, 0600. Each line: sequence number, time, table, operation (insert, update, delete), primary key, the full row after the change (password hashes included, key material only as hashes, never session tokens), prev_hash, hash. The chain runs across files.
  • Write order (write-ahead): append and fsync an intent line, commit the MySQL transaction, append a commit line. Replay applies only intents that have a commit line or whose row is found in the database. S-class changes are rare (account and admin actions), so the fsync cost is irrelevant. Every dump records the last journal sequence read inside its snapshot, so replay knows where to start.
  • Sealing and compaction: a finished day is sealed (final hash recorded, parity created, listed in a manifest). A compaction task can fold old days into a snapshot file of current rows plus the chain head; originals are kept for the retention period.
  • Rejected: MySQL binary log (needs extra privileges and configuration, ties recovery to the server version, not portable); relying on the nightly dump alone (see Q3); triggers writing a journal table (lives in the database being protected).

5. Backup design (RES.30)

5.1 Contents and layout

/data/backups/
  spakr-20261022T030000Z-v0.1.42/        one directory per backup, 0700
    manifest.json                         versions, git tip, journal seq, per-table digests, file list
    SHA256SUMS                            archive, parity, manifest.json
    core.tar[.bz2|.gz]  (+ .par2 set)     database dump, git bundle, journal, redacted config
    media-index.json                      hash, size and path of every original this backup needs
  media-pool/ab/cd/<sha256>/original (+ .par2)   shared across backups, only new files are added

Name: spakr-YYYYMMDDTHHMMSSZ-vVERSION (as in BAK.7), written under a temporary name and renamed when verified; a failed one is renamed .failed.

5.2 Consistent snapshot without stopping the site

  1. Take the backup lock (one at a time) and, for milliseconds, the git write lock; create a temporary ref refs/backup/<ts> at the tip; release the git lock. Git objects are append-only, so the bundle can be built afterwards from that ref (git bundle create ... refs/backup/<ts>), then the ref is deleted. Page saves are blocked for a moment, not for the length of the backup.
  2. mysqldump --single-transaction --routines --triggers --events --hex-blob: a consistent InnoDB snapshot without blocking writers. The last journal sequence is read inside that same transaction. Credentials come from a 0600 option file, never the command line.
  3. Copy the journal up to that sequence.
  4. Reconcile skew by design rather than by locking: S-class tables are self-consistent inside the dump; the derived page index may be a save ahead of or behind the bundle, and the restore ends with reindex (DB.3), which makes git win. Locking the whole site for the dump would buy nothing.
  5. Add the redacted config (RES.31), write the manifest and checksums, compress, create parity, verify (BAK.9), then rename into place.

5.3 Compression: bz2 versus gz, and what to compress

Measured on a synthetic corpus: 5,000 Markdown pages (13 MB of random dictionary words, so real prose will differ somewhat), a 21 MB SQL dump of 200,000 audit-style rows, and 100 MB of random bytes standing in for already-compressed video and images.

Datagzip -6bzip2 -9pbzip2 (4 cores)zstd -3
Pages (13 MB)38.5% in 1.7 s28.7% in 1.0 s28.8% in 0.37 s40.9% in 0.12 s
SQL dump (21 MB)5.5% in 0.21 s3.0% in 1.4 s3.0% in 0.40 s1.5% in 0.03 s
Media (105 MB)100.0% in 3.8 s100.4% in 13.3 s100.4% in 3.5 s100.0% in 0.38 s
  • bz2 does give the smaller file for text and SQL (about a quarter smaller than gz on pages, roughly half the size on SQL) and, in single-threaded form, was no slower than gzip on text, so the owner's default of bz2 is sound for the compressible parts. pbzip2 (Ubuntu package) is 2.7 to 3.8 times faster on four cores and writes standard bz2, so any bzip2 or tar xjf can read it; it is an optional speed-up used if installed.
  • Media does not compress at all and bzip2 spent 13 s per 100 MB discovering that. Compressing media is wasted CPU and, worse, destroys the cheap incremental copy.
  • zstd is faster and smaller than gz, but the owner chose bz2 and gz; it stays a rejected-for-now option so there is one fewer package and format to restore with in an emergency (Q2 lists it).
  • A git bundle is already zlib-compressed packs; recompressing it saves little, so the setting applies to the dump, journal and config members.

5.4 Media: full nightly or incremental

Originals are immutable and named by hash, so "which files does this backup need" is a list of hashes. Copying every original into every nightly archive makes the cost grow with media size times retention: with 20 GB of media and the default 7 daily + 4 weekly + 6 monthly (17 backups) that is 340 GB and over a minute of tar I/O per 10 GB each night. Recommendation: the media pool. Each night, originals not yet in media-pool/ are copied in (with their parity), the backup's media-index.json records the hashes it needs, and retention deletes a pool file only when no retained backup lists it. Restore of any backup reads exactly the originals in its index. Variants are excluded by default (R-class), with a setting to include them. Verification re-hashes pool files against their directory names, so no extra manifest is needed. The trade-off is that a backup is no longer one self-contained file: moving it off-host means copying the directory plus the pool objects it references, and the off-host hook (BAK.17) gets a list of paths rather than one archive. This is Q1.

5.5 Parity defaults

10% redundancy for the core archive is cheap (a few seconds even for large archives) and repairs scattered damage. For media the same percentage is 10 GB of parity per 100 GB, which is a real cost; scattered bit rot needs far less than 10% (Q4). par2 needs the par2 package; BAK.8 gives a clear error when it is missing, and the install guide lists par2 pbzip2 rsync as packages (rsync only if the pool copy uses it; plain Python copy with hash check is the alternative).

5.6 Retention

Defaults as in RES.17: 7 daily, 4 weekly, 6 monthly, all settings (BAK.15). Rules: delete only after a newer backup has verified; never delete the last verified backup; a backup's parity and media-index go with it; pool files are reference-counted by retained indexes. Retention also defines how long erased accounts persist in backups (privacy statement, RES.17). Local retention is no protection against losing the machine; the off-host hook is where that protection comes from (Q5).

5.7 Restore order

  1. Verify SHA256SUMS, then par2 verify; repair if needed. Refuse a backup whose schema version is newer than the software.
  2. Create an empty target; prompt for the secrets removed from the redacted config; write config.json (0600).
  3. Load the MySQL dump. Compare per-table digests with the manifest.
  4. Replay journal entries after the dump's sequence (only present if /data survived or the journal was in the backup; the backup always contains the journal up to its cut).
  5. Run any newer migrations (checked against migration hashes).
  6. Clone the bundle into the content store; git fsck; confirm the tip equals the manifest's.
  7. Restore media from the pool; check each original against its directory name; recreate parity if absent.
  8. reindex (DB.3), media-rebuild (INT.5), requeue-stuck, then a full spakr verify. The report is the proof the restore worked; the daily CI job repeats the cycle on sample content.

7. Open questions for the owner

Each is written to become a decision card: context, options, and the recommendation.

Q1. Is a backup one self-contained file, or a small core archive plus a shared media pool?

Context. The earlier decision was nightly tar.bz2 of all data with a parity file. Media (videos up to 100 MB, images) does not compress, so bzip2 spends about 13 s per 100 MB for 0% gain, and storing every original in every one of 17 retained backups multiplies disk use by 17 (20 GB of media becomes 340 GB).

  • A. One archive, everything inside, compressed. Simplest to move and restore; media copied in full every night; large and slow once media grows.
  • B. Core archive nightly (database, git bundle, journal, config) plus a content-addressed media pool that only receives new files. (Recommended.) Fast nightly runs, disk use equals the media you actually have plus the core archives; a backup is a directory and the pool, not one file.
  • C. One archive per backup but media stored uncompressed inside it and de-duplicated by hard links. Keeps "one file", but hard links do not survive copying off-host or onto another filesystem.

Recommendation: B, because it is the only option whose cost does not scale with retention, and it matches how the media directories already work.

Q2. Which compression for the compressible parts?

Context. bz2 produced the smallest output for text and SQL; gz is the faster, more widely available fallback; zstd is faster and smaller than gz but not in the owner's list.

  • A. bz2 default, gz option, pbzip2 used automatically if installed. (Recommended.) As decided; nothing new to learn.
  • B. Add zstd as a third option. Fastest and good ratio; one more format and package to hold in an emergency.
  • C. bz2 and gz only, no pbzip2. Fewest dependencies; slower on big dumps.

Recommendation: A. Keep zstd off until there is a measured need.

Q3. How much recent change may be lost on a total database loss?

Context. The journal (section 4) gives near-zero loss for accounts, keys, settings and audit, at the cost of a write-ahead file layer and a replay command. Without it, the loss is up to a day (the nightly dump), the same as every other website of this size.

  • A. Build the journal (INT.9 as planned). (Recommended.) Matches the "from the ground up" principle; it is the only way to rebuild MySQL-only data between dumps.
  • B. Skip the journal, rely on the nightly dump, and offer a second dump option (for example every 6 hours) for the S-class tables only. Much less code; up to six hours of account changes can be lost.
  • C. Journal in 1.0 but defer replay tooling. Writes happen from the start (cheap to add early, expensive to retrofit), restore is manual.

Recommendation: A. If the schedule gets tight, C is the fallback.

Q4. How much parity for media originals?

Context. par2 cost scales with redundancy: 5% parity took 1.9 s and 5.6 MB per 100 MB, 10% took 2.8 s and 10.9 MB, 20% took 4.8 s and 21.4 MB. Scattered bit rot needs very little; parity does not help against a dead disk.

  • A. 10% everywhere, one setting. Simple, consistent with BAK.8; media parity doubles the space cost of 5%.
  • B. 10% for archives, packs and journal; 5% for media originals, separate setting. (Recommended.)
  • C. Parity for media only in the backup pool, none beside the live originals. Halves disk use; live files are only repairable from the backup copy.

Recommendation: B.

Q5. Is local-only backup acceptable for the first releases?

Context. Everything above lives in /data on the same machine. It protects against bit rot, deletion and bad upgrades, not against losing the disk or the server. The off-host hook (BAK.17) only runs a command the admin configures.

  • A. Yes, with a loud notice in the admin screen and install guide until an off-host command is set. (Recommended.)
  • B. Ship a documented default off-host command (restic over SFTP) the installer offers to configure. More setup work now.
  • C. Refuse to call the backup healthy until an off-host copy has succeeded once. Strongest, but the status would be red on every fresh install.

Recommendation: A. Revisit B at 0.9 when the install guide is written.

Q6. Should the audit chain head be signed or only anchored?

Context. A hash chain only proves tampering if the head cannot be rewritten along with the rows. Anchoring the head in the journal and every backup manifest catches edits made after a backup. An HMAC with a key from config.json would also catch an attacker who has database access but not the config file, but adds a key that must be kept and rotated.

  • A. Anchor in journal and backup manifests, no key. (Recommended.)
  • B. Anchor plus HMAC with the existing application secret. Stronger; losing the config makes older checkpoints unverifiable until the secret is re-entered.
  • C. Skip the chain, rely on an append-only table. No tamper evidence.

Recommendation: A for 1.0; B can be added later without a format break because the checkpoint record has a version field.

Q7. How often should the full media check run?

Context. Re-hashing is cheap in CPU (79 ms per 100 MB) but reads every byte; par2 verify reads it again (0.76 s per 100 MB).

  • A. Daily light check; weekly hash of a rotating one-seventh slice of media; monthly par2 verify of everything. (Recommended.) Every file is re-read at least weekly with a bounded nightly load.
  • B. Weekly full hash plus monthly par2. Simple; one heavy night a week.
  • C. Admin-triggered only. Nothing scheduled; rot is found late.

Recommendation: A. All values are settings.

Q8. May git commits carry an opaque permanent user identifier?

Context. To rebuild page_revision.author_id from git alone, each commit author must map back to a user. Using emails would leak them to anyone with a clone and could not be erased. An opaque id such as u-7f3a9c, stored in user.public_id and used as the git author name with a placeholder domain, solves both and keeps erasure possible (clear the user row; the id means nothing). This touches the content model, which the sibling "content model and exchange" thread is deciding, so it should be settled once, there.

  • A. Yes, opaque stable id in the commit author. (Recommended.)
  • B. Author is the display name at commit time. Readable history, but renames and duplicates break the mapping.
  • C. No author in git; authorship only in MySQL. Authorship is then not rebuildable and history loses attribution after a database loss.

Recommendation: A.

Q9. Where do the final integrity and backup specifications live?

8. What I could not verify

  • mysqldump --single-transaction, the journal write-ahead order and the MySQL-side parts were not run: there is no MySQL server in this environment. They follow documented MySQL behaviour and are re-checked when DB and BAK items are built.
  • The compression corpus is synthetic; ratios on real prose and real video will differ in absolute terms, though the ordering (bz2 smaller than gz on text, nothing on media) is reliable.
  • par2 numbers are from a 100 MB file of random data on four cores; repair time on a real disk with cold cache will be dominated by reads.
  • Multi-gigabyte par2 behaviour (block-count limits, memory use) was not tested.
  • Filesystem-level protection (ZFS, btrfs, dm-integrity) was only reviewed, not run.
