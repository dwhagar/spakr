Content model and exchange

Status: draft design for review, 2026-10-22. Closes RES.13 (entity field definitions and front matter schema) and RES.19 (import and export formats). Unblocks ENT.1 to ENT.14, GIT.9, LNK.3 and OPS.6. Extends Database design; where the two disagree, this page is the proposal and says which table changes. The sibling page Integrity, parity and backup (RES.26 to RES.30) owns parity, backup archives and restore, and classifies every table as source of truth (S), rebuildable (R) or disposable (D); this page follows that classification (section 3.2) and only says what exchange files contain and how they are read safely.

Summary

  • One page = one Markdown file. A YAML front matter block holds everything that is not prose: common header, one lead image, the typed fields (the infobox) and the relations. The body holds only prose. The two are never mixed: no field lives in the body and no prose lives in a field.
  • Types are described by data, not code. A type registry (one small YAML file per type, shipped with the software) lists the fields, their kinds, labels, infobox order and which vocabulary they draw from. The same registry drives validation, the editor form (ENT.13), the infobox (ENT.14), search filters (SEARCH.4), the OpenAPI schemas and import.
  • Front matter is YAML read by a hardened loader. Measured here: PyYAML's default loader turns no into false, 0750 into 488 and 2001-02-03 into a date, so a "size: no" or a language code NO would be silently corrupted. A subclassed loader fixes all three, rejects anchors and tags, and parses a page in 0.13 ms (default: 0.93 ms).
  • Exchange has one native format and two friendly ones. The native bundle is a zip whose page entries are byte-identical to the files in git, so export then import is lossless and cheap. A plain folder of Markdown files (Obsidian-style) and CSV per type cover editing outside the site and bulk entry from a spreadsheet. Everything else is post-1.0.
  • Export never widens access. It contains exactly what the requester may see, GM-only pages included only for GM and admin. Import runs the same validation as the editor and is dry-run first.
  • Authorship in git (their Q8): commits carry an opaque permanent user id, never an email or display name, so page_revision can be rebuilt after a database loss. It is commit metadata, not front matter (section 2.5).
  • Six decisions only the owner can make are collected at the end ("Open questions for the owner"), each with options and a recommendation.

1. Principles

  • Git holds the truth, MySQL is a rebuildable index (RES.29, GIT.9). Therefore every non-derived datum is in the file and every column the index holds about fields is recomputed by spakr rebuild-index. Derived data (created, updated, author, revision, current commit, content hash) is never written into the file; it comes from git, and a hash of a file cannot sit inside the file.
  • System-agnostic rules content (decided): stat blocks, dice, costs, dates and measures are free text. Typed fields exist to label, browse, filter and link, not to calculate.
  • Readable and hand-editable. Someone with only a text editor and the git repository can read, fix and write a page. Keys are English snake_case, references are type/slug, and the server writes the block in a fixed key order so diffs show only what changed.
  • Lenient on read, strict on write. A page already in git is never made unreadable by a later vocabulary or schema change: unknown keys and retired vocabulary codes are kept and flagged. New writes through the UI, API or import are validated and rejected with a field-level error.
  • One mechanism for links. A typed reference field and a free relation both end up as rows in relation with a kind from the admin-managed vocabulary, so backlinks, browse and visibility filtering exist once.

## Background
...

The file starts with --- on the first line and the block ends at the next line that is exactly ---. Everything after is the body, passed to the renderer untouched. Line endings are normalised to LF and a leading BOM is dropped on read; the writer always emits LF, UTF-8, NFC, with a single trailing newline.

2.4 YAML subset and loader

PyYAML 6.0.3 (already chosen) with a hardened loader, tested in poc/frontmatter_poc.py. Measured on this machine (PyYAML with libyaml):

Rules: only the loader's own booleans are true and false; integers are plain decimal with no leading zero; there is no timestamp type; anchors, aliases and explicit tags are errors; the block may not exceed 32 KB or nest deeper than 4 levels; duplicate keys are errors; every value must be a string, integer, boolean, list or mapping. The writer is the only producer in normal use: it dumps with a fixed key order, block style for the registry-defined structure, always double-quotes strings that would otherwise resolve to anything other than a string, and never emits flow style except for the two documented one-liners (image, a relation). Applying the registry kind on read means a value for a line field that is not a string is coerced back to its source text where possible and flagged otherwise.

2.5 Authorship lives in the commit, not the file

This answers question 8 of the integrity and backup page. Who wrote a revision is stored in git commit metadata and never in front matter (it is derived data, and a file cannot honestly contain the commit that changes it). To make page_revision.author_id rebuildable from git alone, the content store writes every commit as:

author/committer name   u-k3m7q9x2p4          (user.public_id, random, permanent, never reused)
author/committer email  k3m7q9x2p4@users.spakr.invalid   (.invalid is reserved and never resolves)
message                 first line: edit summary (or "Edit <title>"); trailers where relevant:
                        Reverts: <sha>   Import-Id: <id>   Renamed-From: <type/slug>
  • The id is generated once when the account is created (10 characters from a 32-letter alphabet, collision-checked) and stored in user.public_id. It is not secret, but it is opaque: it holds no email, name or sequence, so a clone of the repository (backups, bundles) exposes no personal data.
  • Display name and profile are looked up from the user table at read time, so renames take effect on all old revisions. Erasing a person clears the user row; the id remains in history and means nothing (the pseudonymous identity RES.29 relied on, with no history rewrite).
  • System actions (setup seed, schema migration of front matter, import under a service key) use a reserved id u-system; imports use the importing user as author.
  • Rebuild: spakr rebuild-index maps public_id to user.id for page_revision; an id with no user (account erased or database lost) becomes author "unknown" with the id kept in the row.
  • If the owner chooses their option B or C, the front matter and exchange formats do not change; only the commit writer and the rebuild mapping do. I therefore recommend option A and add no separate question here.

3. Type registry and field lists

3.1 Approach

Each type is one YAML file shipped in the package (src/spakr/schema/types/character.yaml and so on) plus a vocabulary seed file. At start-up the registry is loaded, checked (unique keys, known kinds, existing vocabularies and target types) and exposed as a Python object and as JSON at /api/v1/schema (ENT.13). A migration seeds vocabularies. The schema has an integer schema_version that counts up on any change and is reported by the status endpoint next to the API and database versions. The registry also generates the OpenAPI component schema per type, so documentation and validation cannot drift (RES.14 chose a hand-written description; this part is generated from the registry into it).

The index stores fields in one narrow table instead of one table per type:

page_field(page_id, field_key, position, value_text NULL, value_int NULL,
           value_bool NULL, ref_page_id NULL)
  primary key (page_id, field_key, position)
  index (field_key, value_text(100)), index (field_key, value_int), index (ref_page_id)

A ref value is stored here and also written as a relation row with the field's declared relation kind, in one transaction (the field row exists for display order and form round-tripping; the relation row is what backlinks and traversal use). A search document (SEARCH.2) takes the text of line, lines and choice labels, not the titles of referenced pages (section 6).

Change to the database design: the nine type tables in Database design are replaced by page_field, so DB.2 no longer adds them. Everything those tables held is expressible; indexes are per field key. Reason: adding or retiring a field becomes a registry change plus spakr rebuild-index, not an Alembic migration per type, and a rebuild from git is one loop over pages instead of nine table writers. The cost is slightly more awkward SQL for multi-field filters (one join per filtered field); for browse by type plus two filters on a few thousand pages this is a few milliseconds, to be confirmed by a benchmark in ENT.1 before the old tables are removed from the plan.

3.3 Common infobox

The infobox is rendered from the page's image and fields only, in registry group and order, beside the prose on wide screens and stacked above it on narrow ones (ENT.14). Empty fields are omitted. A ref becomes an entity link chip, subject to section 6. Nothing about the infobox is ever inferred from the body, and editing the body never changes a field.

  manifest.json             format, versions, scope, requester role, counts

  schema.json               registry snapshot (types, fields, vocabularies, settings, relation kinds)

manifest.json carries: format (spakr-bundle and its integer version, 1), software_version, api_version, db_version, schema_version, exported_at, exported_by (username), role at export, scope (everything visible, or filters: type, setting, tag, since), include_media, counts, and a hidden_note that says pages the requester could not see are absent. Identifiers (database ids, user ids, commit hashes) never leave: the page files carry slugs and type/slug references only. Authorship and history are not exported; the import records the importer as author. The full history is the git bundle of the backup (RES.17, RES.30), not an exchange format.

Round trip rule, tested in ENT/OPS: export then import into an empty install of the same or a newer schema yields byte-identical page files, identical rebuilt index rows for fields, tags, settings, relations and former slugs, and identical search results. Import into an install with different vocabularies keeps unknown codes and reports them. Media is matched by SHA-256, so image references survive; a bundle without media imports with red media references the media library can resolve later.

4.3 Import procedure

  1. Upload and queue. The file is stored as an upload in quarantine and an import task runs on the Redis queue; nothing is written to the content store at this step.
  2. Safe open. Entry names must be relative, contain no .., no symlinks, no absolute paths, no names outside manifest.json, SHA256SUMS, schema.json, pages/<type>/<slug>.md and media/...; nested archives are not opened. Limits (configurable): 500 MB uncompressed, 50,000 entries, 25 MB per page file, compression ratio 100:1 per entry. Hashes in SHA256SUMS must match.
  3. Parse and validate all pages in memory with the hardened loader and the registry (2.4), the slug rules of GIT.6, and the body size limit. Collect warnings and errors per file; a file with an error is skipped, the rest continue.
  4. Dry run report (always produced, JSON and an HTML view): counts of create, update, unchanged and skipped, a table of conflicts (page exists with different content), warnings (unknown keys, retired or unknown vocabulary codes, dangling references, missing media, visibility changes), and the permission checks. The user confirms; an admin can mark an import as pre-approved for scripted use (?apply=true with an API key that has the permission).
  5. Apply in batches of 100 pages under the write lock (RES.4): write files, one git add and one commit per batch with the importer as author and a message Import: <file> [import <id>] (n pages), then update the MySQL index and search documents inside the same lock hold, as for a normal save. A failure stops the run, leaves earlier batches committed, and reports exactly which. revert import <id> reverts the batch commits (new commits, history never rewritten, GIT.4).
  6. Media from a bundle goes through the normal upload pipeline (type sniffing, ImageMagick/ffmpeg re-encode, hashes, quarantine rules) like any upload and is never trusted because it came in a bundle; matching hashes reuse existing media.
  7. Audit: one audit entry for the import with counts and the report path; the report is kept for 30 days.

Conflict policy (chosen at upload, default "skip existing"): create only (existing pages are skipped), update (existing pages get a new revision when content differs, otherwise unchanged; the user sees the conflict list first), replace (as update but body and fields come wholly from the file). There is no mode that deletes pages absent from the bundle. Protected pages (SEC.26) and pages the importer may not edit are skipped and listed.

Single-page upload and CSV use the same pipeline with a one-page or field-only scope. CSV updates change only the columns present and write the new front matter through the same writer, so the body is untouched and the diff is a front matter diff.

4.4 Export procedure

  1. Request with filters (type, setting, tag, since a revision or date, include media, format). Allowed for any signed-in role and anonymous callers only for the public subset if the admin enables it (default off, since bulk scraping).
  2. The query selects pages through the single visibility filter (VIS.2), so GM-only pages appear only for users with the GM or admin role (and API keys carrying those permissions).
  3. A queue task streams entries into a zip under /data/exports/<random 128-bit>/ (mode 0600), reading each page file straight from the working tree (0.02 ms each from cache) and writing the manifest last. Nothing is built in memory beyond one page at a time.
  4. The requester gets a one-time authenticated download link; files are deleted after 24 hours and by the maintenance job. Each export is an audit entry; it is the only place where GM content leaves the system in bulk, so the log notes role and scope.
  5. CSV cells that begin with =, +, -, @, tab or CR are prefixed with a single quote so a spreadsheet cannot execute them.

4.5 Measured

From poc/frontmatter_poc.py (this machine, Python 3.13): a bundle of 5,000 page files of about 650 bytes (front matter plus a short body) compressed to 1.6 MB; writing took 0.23 s, reading with hash verification and size checks took 0.13 s, and every file came back byte-identical (5,000 of 5,000). Parsing the front matter of 5,000 pages with the hardened loader took 0.85 s including anchor checks. The file-time costs of the git batch (about 26 ms for one commit of one file, RES.4) are expected to be amortised across 100 pages; that was not measured here and should be before OPS.6 is sized. Real pages are about 2.5 KB (RES.29), so a 5,000-page site is about 13 MB uncompressed and a few seconds to export.

5. Security

  • YAML: hardened loader (2.4): no anchors, aliases or tags (alias bomb, object construction), size and depth caps, duplicate keys rejected, no implicit typing surprises that change data.
  • Zip: traversal and symlink checks, limits on count, size and ratio, entry-name whitelist, hash manifest verified before parsing, no extraction to disk (entries are read from the archive), no nested archives, archives kept in quarantine until processed.
  • Content from outside is untrusted exactly like editor input: the body is sanitised at render time as always (html sanitising, RES.3); infobox line values go through the same inline Markdown path and the same sanitiser; titles and aliases are escaped on output; slugs follow GIT.6; media is processed, never copied.
  • No privilege through the file: an imported page cannot choose its author, timestamps or id; visibility: gm and any change of visibility are honoured only when the importer is GM or admin; since import itself is a GM and admin permission by default (open question 6), a lower role that is later granted it can create and update public pages only, and cannot touch existing GM pages. Reference fields cannot reach pages the importer cannot see: they are stored as text and resolved at read time under the viewer's visibility.
  • Permission content.import (default GM and admin), content.export (default every signed-in user, scoped by visibility), both assignable to API keys but never wider than the owner's rights. Rate-limited and queue-limited (one import per user at a time).
  • Export is a leak risk: unguessable path, 0600, authenticated download, expiry, audit; the manifest states the requester's role so a bundle can be recognised as GM-level (backups of the same data are already treated as GM-level).
  • Information leaks around GM-only pages: section 6.
  • CSV injection on export (4.4); CSV import never evaluates anything, is UTF-8 only and rejects cells over the field maximum.

6. GM-only handling

  • Storage: visibility: gm in the front matter (key omitted for public). The index column page.visibility mirrors it; the file wins on rebuild. Changing it is a normal revision.
  • Granularity in 1.0 is the page (decided: GM-only flag). Field-level and section-level secrecy are not offered (open question 2). The stable workaround is a linked GM-only companion page.
  • References from visible pages to GM-only pages. A ref or relation to a page the viewer cannot see is omitted entirely from the infobox, related list and API output, not shown as plain text: the target's title is itself the secret (RND.7 unwraps body links but body text is written by an author who chose those words, a field's text is the target's title). The count is not revealed either.
  • Search. The search document of a page contains its own text and line fields but not the titles of referenced pages, so a public page's searchable text cannot reveal a GM page. Field search on references goes through the relation table with the visibility join at query time (SEARCH.4), which also means flipping a page between public and GM requires reindexing that page only, not its referrers.
  • Rendered cache and API shape: the fields JSON and infobox are produced after the visibility filter, never cached per page without the viewer's visibility class in the key (RND.5, RND.7).
  • Export and import: sections 4.3 to 5. A bundle made by a non-GM contains no GM page and no mention of one except the manifest note that hidden pages are absent (without a count).
  • Reserved: visibility_group in front matter and page.visibility_group_id (decided). In 1.0 a file containing the key is rejected so nothing silently starts meaning something later.
  • Raw repository: remains private; history, diff and blame are served only through the visibility filter (RES.29).

7. Efficiency

  • Reading a page for display never parses YAML: the render cache (RES.25) and the index serve it. YAML is parsed on save, on rebuild, on import and for the editor form.
  • Rebuild of 5,000 pages: file read 0.09 s (RES.29) plus front matter parsing 0.85 s, then index writes in transactions of a few hundred pages. The hardened loader matters here (about five times faster than the pure-Python default).
  • Registry is loaded once per process (a few KB); the form schema JSON is served with a version ETag.
  • Fields as rows: one write per field per save (up to about 15), indexed lookups per key; fine for thousands of pages. Browse by type plus up to two filters is a self-join per filter; benchmark in ENT.1 against 20,000 pages before locking the choice.
  • Bundles stream; import holds the git lock per batch, not for the whole run, so editors are not locked out for the duration of a large import.

9. Alternatives rejected

AlternativeWhy not
Nine type tables in MySQL (current database design)Every added field is a migration; rebuild needs nine writers; schema as data is impossible. Kept as a fallback if the ENT.17 benchmark shows the field table is too slow.
JSON column per page with generated columnsFast to build, but indexes need one generated column per filterable field (a migration again), and cross-page reference joins are awkward. It is the second choice if page_field proves slow.
JSON or TOML front matterJSON has no comments and is hard to hand-edit; TOML nests lists of tables badly. YAML is already the chosen format (RES.1) and is made safe by the loader.
Fields in a sidecar file next to the pageTwo files per page: renames and reverts are no longer one atomic change, and merging histories gets harder. Front matter keeps one file, one commit, one hash.
Infobox as a template in the body (MediaWiki-style {{Infobox ...}})Needs a template engine, mixes data with prose, cannot be validated or searched without parsing prose, and the owner asked for fields separate from page text.
Typed numbers, dates, money and diceRule-system specific; the owner's decision is free text. A later optional field kind can be added without changing old pages.
Stable UID in front matter and references by UIDSurvives renames without rewriting referrers, but makes files unreadable and hand-editing error-prone. Instead: type/slug references, former_slugs resolution and (GIT.6) a rename that rewrites the referring field values in the same commit. The index stores resolved page ids, so lookups are by id.

tar or tar.gz for exchangeNeeds streaming to inspect; zip allows validating the manifest before reading entries and is openable by non-technical GMs. Backups stay tar.
XLSX, ODS, PDF and static HTML exports in 1.0Extra libraries, new attack surface and no round trip. CSV and Markdown cover the spreadsheet and offline-reading cases; print stylesheets cover paper.
Stripping all GM pages from a non-GM export silently versus noting their absenceA note without a count tells the reader the bundle is incomplete without leaking how many pages exist.

10. What was not verified

  • Timings are from this sandbox with PyYAML 6.0.3 and libyaml, Python 3.13; Ubuntu 24.04 ships Python 3.12 and may differ, and the target app environment is a virtualenv (RES.15). Absolute numbers will change, ratios should not.
  • The field table's browse and filter performance is reasoned, not measured (ENT.17).
  • Batch commit speed for 100 pages and the effect on concurrent editors were not benchmarked.
  • Importers for other tools were not studied; their formats are unverified here.
  • No one has yet tried the field lists against real campaign material; the lists are a first pass from the plan's type table and common game-database practice and are expected to change during ENT.2 to ENT.11, which is why the registry is data.

Open questions for the owner

For the TODO thread to turn into decision cards. Each has context, options, a recommendation and what depends on it. Nothing below blocks starting GIT.9 or ENT.1; question 1 and 2 change what those build, so they are most useful early.

Q1. Can admins add their own fields and types, or are field lists fixed by the software?

Context: The registry is data, so both are possible. Your game may want fields this design does not know (a custom attribute, a faction rating). Fixed lists are simpler to document, test and keep stable across upgrades; editable lists add an admin screen, validation of changes, and the need to migrate pages when a field is retired.

  • A. Fixed per release, admins manage only vocabularies (categories, kinds, statuses, relation kinds, settings). Custom needs are met by the body text and by the reserved x_ keys.
  • B. Admins can add fields to existing types (kinds from section 2.3 only), retire them, and order them; types stay fixed.
  • C. Admins can also define new types.

Recommendation: A for 1.0, with B scheduled for 1.x because the storage and form generation already support it. Fewer moving parts to get a stable 1.0 and a clean upgrade path. Affects: ENT.1, ENT.13, UI.7.

Q2. How secret can GM-only content be inside a mostly public page?

Context: The decided GM flag is per page. A public NPC page with one secret (the villain is secretly her brother) would need a second, linked GM page. Finer control exposes secrets through search snippets, the render cache, history and diff, and exports unless every path honours it.

  • A. Page-level only (the current decision), use companion GM pages. References to GM pages are hidden from non-GM viewers (section 6).
  • B. Page-level plus GM-only fields (a field marked GM in the registry or per page).
  • C. Page-level plus GM-only sections in the body.

Recommendation: A; revisit B after 1.0 together with visibility groups (the key is reserved). Every extra granularity multiplies the leak tests (VIS.3). Affects: GIT.9, VIS.1 to VIS.3, SEARCH.2.

Q3. Are the per-type field lists right?

Context: Section 3.4 is the first draft: roughly 5 to 9 fields per type. Fewer fields means less typing but less to browse and filter on; more fields means more empty infoboxes. Two specific choices: should characters carry a status (alive, dead, missing) and character_kind (player or non-player)? And should there be a "played by" field? The latter would put real people's names in public data, which I advise against.

  • A. Approve as drafted, tune during ENT.2 to ENT.11 with real pages.
  • B. Trim to a minimum (about 3 per type, the rest in the body), fastest to build and easiest to remember.
  • C. Expand now with fields you name for particular types.

Recommendation: A (with no "played by"). The lists are cheap to change before ENT starts because they are data. Affects: ENT.2 to ENT.11, ENT.14, SEARCH.4.

Q4. Which relation kinds should ship in the starter vocabulary?

Context: Section 3.5 lists 18 kinds. The vocabulary is admin-editable afterwards, so this only sets the starting point. Family ties (parent of, partner of, sibling of) are common in character-driven games but are nine more kinds if covered in full.

  • A. The 18 kinds as listed, with related_to for anything else.
  • B. A plus a small family set (parent_of with inverse child_of, partner_of, sibling_of).
  • C. Smaller: only the kinds that fields write, plus related_to.

Recommendation: B. Family ties are the one relation people always want and a relation note covers the rest. Affects: LNK.3, LNK.6, ENT.2.

Q5. Which exchange formats are required for 1.0?

Context: The bundle is the only format needed to move a world between installs and is nearly free given the page file format. The Markdown folder and CSV are the formats most likely to be used day to day (editing in a local tool; filling a spreadsheet). Each added format is code to test and a surface to secure; wiki converters need the other tool's format studied first.

  • A. Bundle and single-page .md only.
  • B. A plus Markdown folder import and CSV import/export (as in 4.1).
  • C. B plus converters for named tools (you name which; each needs its own research item).

Recommendation: B. It covers editing outside the site and bulk entry, which are the realistic needs, without third-party formats. Affects: OPS.6, DOC.4, test plan.

Q6. Who may import and who may export?

Context: Import can create or change many pages at once (it is revertible as a batch). Export of everything a GM can see is a bulk copy of GM-only content; of everything public it is a scraping convenience.

  • A. Import: GM and admin; export: any signed-in user for what they can see; anonymous export off.
  • B. Import: editors too (with the same validation, no visibility changes above their role).
  • C. Both admin only.

Recommendation: A. Importing is a power tool, and export respects visibility, so no new secret can leave. Roles are still assignable per API key. Affects: OPS.6, AUTH.8 (permission list), SEC.

(Smaller points decided here, not needing a card: one lead image per page; galleries are body media; export contains no history; rename rewrites referrers; dates and measures are free text. Say so if any should change.)
